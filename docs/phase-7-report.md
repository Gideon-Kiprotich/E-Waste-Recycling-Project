## Behavior and decisions

Pickup requires the named active scoped Collector, current Accepted eligibility binding/outstanding reservations, and an approved unfinished/unconsumed proposed route stop. Drop-off requires current Ready review, the request's selected active reviewed subtype-compatible collection point, and an active Processor explicitly scoped to that point and its organization. Administrator **Point staff access** grants/revokes only existing Processor accounts; actual changes increment account/session/membership versions and delete affected sessions. Same active scope is an audited no-op. Scope/approval is checked again on use; no inferred scope or Consumer conversion exists.

Old permanent EWC QR URLs remain valid for Consumers; staff opening one receives context guidance without querying/disclosing another owner's item. POST lookup is limited to authorized visit rows. Wrong codes produce generic feedback and an opaque `context_mismatch` record without retaining the attempted foreign code. Optional camera scanning requests permission only on explicit action, accepts same-origin EWC labels, stops the stream and fills the manual field without submitting receipt. Unsupported/insecure/denied/failed scanning leaves the manual workflow available; permission is not repeatedly requested on the page. No new dependency or external scan service is used.

One transaction records a visit per request. Explicit outcomes are received/absent/refused/mismatch/safety_hold; submitted “untouched” rows and omissions have no attempt/outcome and remain reserved. Each Received row requires an explicit physical category/subtype/model comparison/actual receipt attestation; mismatch/hold cannot be combined with that attestation. Private observations/reasons are encrypted. Observed time is entered in UTC at minute precision, bounded from the request's submission minute through now; server-recorded UTC time is distinct. Nothing is inferred about signatures or Consumer presence/login.

Every visit requires one private JPEG/PNG/non-active PDF (5 MiB maximum; images re-encoded without metadata) or accountable operator reference issuer/record number with a receiving-staff declaration. Encrypted references retain asserting actor and provenance: **staff assertion, not independently verified evidence**. They are never fetched. Downloads require recording actor plus current authorized organization/point context, use private/no-store headers, download disposition and a sandbox policy; Consumers/Admin oversight get safe summaries, not private observations/evidence. Private inputs and uploads are not flashed after errors.

Only Received rows get a unique `first_receipts` entry per canonical subject, immutable subject event, incremented subject/custody/request versions, item `received`, request item `collected`/inactive and confirmed recipient custody. Attempt outcomes are append-only and tied to the visit's monotonic request version. Owner party → Collector user party for pickup or → collection-point party for drop-off; actor is separately retained. Ownership, identifier encryption/hashes and HDD/SSD YES data status/facet identity remain unchanged. Failed/untouched items retain original custody/reservations. Partial header state is derived; mixed final collected/cancelled is COMPLETED with per-item outcomes, not “all collected.”

Pickup assignment terminal states add `completed` and `remainder_review`; every attempted pickup consumes/closes that assignment, even with no receipt. Eligible remainder needs fresh review/offer/acknowledgment/route. Drop-off remainder needs fresh review only. Physical mismatch/safety-hold discrepancies block future Ready/receipt pending a reviewed correction; no override/resolution control is introduced. Late/stale/conflicting fresh claims retain a bounded opaque exception (request/actor/type/server time, without copying the rejected private payload or foreign code) and never override custody. Authorized exact retries reauthenticate/recheck scope, then return the original safe visit before current assignment/version gates; changed payloads conflict. Upload bytes enter the keyed command comparison; retries create no new files/notices/events/custody.

## Route execution and finality

Frozen runs/results, original routes/stops/dependencies and approval history remain immutable. `route_consumptions` links each executed stop to its visit. `receipt_route_changes` records exact before/after projections, constrained to that visit's own request, accepted assignment and received subjects/request items. Deferred checks require the final rows to match. Only those exact receipt-driven changes preserve that same run's approval; no session flag, disabled trigger or generic “ignore invalidation” switch exists. Current execution compares frozen dependency fingerprints or those exact receipt-linked projections and rechecks unconsumed jobs' live eligibility/date. Nullable point-scope metadata is omitted from Collector membership fingerprints for compatibility with existing Phase 6 snapshots.

Expected changes: own request version/state/stale review; own assignment terminal state/active/version; received subject version and received request-item outcome/active flag. Unrelated dates, self-reports, cancellations, reviews, account/scope status, directory/capabilities, service area, coordinates/private details and vehicle changes still invalidate approval and release claims normally. A newly elapsed date blocks remaining work even without a row update. Receipt at stop one permits still-valid stop two; this does not recalculate or claim actual travel metrics.

Consumption releases only its assignment claim. Vehicle/Collector claims remain until explicit finish/invalidation; deferred exact-set guards check the remaining claims at the enforcement boundary. The named Collector's **Finish tour work** requires the exact displayed unfinished list and explicit acknowledgment/reason. It records those stops as unfinished, releases tour claims and preserves their accepted assignments/item reservations for Administrator replanning. It creates no attempt/receipt for omissions. An approval becomes finished only after all proposed tours explicitly finish; unrelated invalidation/supersession/withdrawal retains its existing semantics. No finish establishes depot arrival/unloading/delivery/facility receipt.

All mutations use the existing advisory transaction gate, deterministic subject/item/request/reservation locks, current actor/version checks and retry-first commands. Database PK/FKs, append-only triggers, valid actor/point/assignment guards, deferred receipt/custody/event/outcome/claim projections and named first-receipt uniqueness protect finality. Only the named first-receipt uniqueness conflict maps to a safe conflict; unrelated database failures propagate. On rollback, only newly stored unreferenced evidence is removed; retained/shared files are untouched. Supported receipt notices deliver independently from committed outbox rows, deduplicate by outbox ID and never drain unrelated historical pending rows or send email.

## Exact walkthroughs and acceptance status

1. **Pickup:** Administrator finishes **Operators and places**, **Collector access**, vehicle declaration, then **Request review → Ready for later allocation (current checks must pass) → Record review decision**, **Pickup allocation → Review allocation**, choose **Offer pickup job** with the scoped Collector and compatible receiving destination, then **Record assignment action**; named Collector **Offers and accepted work → Open assignment → Accept — not scheduled → Record response**, Administrator **Route planning → Freeze and compare routes → Approve proposed plan**. Collector **Approved routes → Open ordered stops → Record pickup visit**; optionally **Select label** or **Scan with camera**, physically compare, set each outcome/attestation, actual UTC time, private observation and evidence/reference; **Record visit outcomes**. Consumer **My requests → Request detail → View safe visit outcomes** sees only owned milestones. Approval/acceptance alone never changes custody.
2. **Drop-off:** finish reviewed processor/both operator and exact point capabilities, then Administrator **Point staff access → Link or reactivate at selected point → Save point scope** for an existing Processor. Processor signs in again. Consumer submits drop-off for that point; Administrator records a current Ready review after directory setup. Processor **Point intake → Open drop-off visit**, compare labels/items and complete outcomes/evidence/time, then **Record visit outcomes**. No Collector offer or route is required. Scope loss/other point/stale review blocks receipt.
3. **Partial/failed:** choose only actual attempted outcomes, leave other rows **Untouched — not attempted**, supply private reasons/evidence/time and submit. Verify only received custody/reservations change and absent/refused/untouched rows remain reserved. Pickup assignment shows **Visit recorded — remainder needs fresh review**; renew eligible remainder through review/offer/acceptance/routing. Drop-off remainder renews review only. Mismatch/hold remains blocked pending reviewed correction, with no override button.
4. **Multi-stop:** record first visit, select **Continue Approved routes**, open the same ordered tour and record the next still-valid stop. Recorded stops link to their outcomes, not live contact details; consumed pickup coordinates are omitted from the map. Staff receipt attachments use the visit FK, separate from owner-visible registration-photo links. On completing or stopping tour work, inspect the explicit unfinished list, enter **Private finish reason**, acknowledge remaining stops uncollected and press **Finish tour work**. Confirm only route claims release; unfinished assignments/reservations remain for a fresh comparison/approval, with no inferred attempt/arrival/unload/delivery.
