## Assurance policy and implementation

[The assurance specification](evaluation/phase-10a-assurance-specification.md) recorded the transitions, compatibility choices and expected cases **before implementation**. It cites the verified official NIST SP 800-88 Rev. 2 (September 2025) assurance/documentation guidance and current official Seagate method/support guidance. These inform project policy, not certification or universal efficacy. S11 supplies the context/gate/history composition; existing Blade components, project CSS, accessible feedback and role navigation are reused. No prototype scripts, invented legal mandates, destructive commands, fabricated logs, automatic release or new Stitch export were imported.

Frozen **MEDIA-ASSURANCE-1.0** is migration data with a checksum verified by the action, an immutable singleton policy and no arbitrary policy substitution. Supported combinations are evidenced **HDD firmware sanitize overwrite / CLEAR**, **SSD firmware sanitize block erase / PURGE**, and **HDD/SSD media shredding / DESTROY**. Actual model/firmware/interface support, scope, applicable destruction criterion and results must be evidenced and reviewed. Other clear/purge/destroy and unknown techniques are record-only, including crypto erase/degaussing/formatting; broad labels alone cannot satisfy the gate. Logical success requires software version; shredding instead requires equipment identity and documented criterion/procedure. No universal particle-size value or manufacturer support is assumed. Future policy expansion requires a separately frozen resource and reviewed forward migration; never edit the 1.0 resource to change historical meaning.

`RecordSanitization` uses separate attempt, verification, validation and applicability-revalidation commands under the existing global transaction gate, current actor/session checks and lock order. The request's explicit version and keyed dependency token reject stale forms. Retry authorization precedes the historical same-command return, which precedes mutable prerequisites/version checks; changed payloads conflict and successful old retries never restore an obsolete gate. Each new attempt links the preceding physical attempt and each operation links the preceding immutable assurance record.

`sanitization_records` is one immutable ledger distinguished by kind, with self-references to the physical attempt, frozen policy, actual actor/access, observed/recorded times, subject/inspection/decision/custody/facility/operator versions, command/event and private evidence. Executor, tool/version, scope, procedure, reasons and operator references are encrypted. Failures/incomplete/unverifiable work may honestly omit unavailable metadata/evidence; reported success requires applicable full metadata/evidence. When negative work has unknown execution time, record the actual observation of the failure/report and explain that limitation, never a fabricated execution time. Every review requires its own evidence/reference and reason. An uploaded certificate cannot perform the separate review commands. Positive verification/validation requires all versioned applicable checks YES; uncertainty is not silently converted to a pass.

The minimal `sanitization_current` projection retains only the latest ledger pointer/attempt, consecutive assurance version and destruction flag. Database guards enforce current scoped facility eligibility, accepted custody, non-HOLD decision, absence of disputes/hard restrictions, compatible media, stage ordering, positive checks, evidence attribution, immutable ledgers/policy and reciprocal command/event/projection references. Deferred checks are explicitly forced in tests, including an insert that succeeds before its missing reciprocal projection/event is rejected. Root-transaction races and commit-time rollback/file cleanup are also exercised.

The assurance version uses the `sanitization` workflow namespace in `domain_events`; **both `subject_id` and `aggregate_id` are the existing canonical drive subject ID**. This is an assurance command sequence, not a new storage/physical identity or custody stream. No second facet/owner/code/data-status record is created. ## Gate transitions and recovery

- No attempt: **Data treatment required**. Reported success: **Reported success — verification pending**. Failed/incomplete/unverifiable attempts are retained blocked outcomes, even when metadata is unavailable.
- Separate satisfactory execution verification: **Execution verified — adequacy validation pending**. Negative/unverifiable verification requires a new real attempt; it cannot be edited or replaced by an optimistic review.
- Separate accepted adequacy validation: **Data treatment satisfied (attested)**. Rejection requires a new attempt. This is a bounded data-treatment assertion, never reuse suitability, certification, work release or disposal. HDD/SSD remain YES permanently.
- The newest attempt/review always governs. A new negative attempt supersedes old clearance without deleting it; historical success is never used as an automatic fallback.
- Any reported destruction attempt, including partial/failed/uncertain destruction, retains **Destruction reported — non-reusable** permanently. History separately labels reported destruction, verified execution and accepted adequacy. Only a supported destruction attempt can subsequently satisfy data treatment; later ordinary logical success cannot erase damage/non-reusability concerns. Accepted destruction preserves identity/custody/YES and establishes no disposal/dismantling/closure.
- Current dependency drift produces **Applicability review required — no current clearance**. Missing decision/hold/scope/capability/dispute prerequisites must first be resolved legitimately. Previously accepted latest evidence can receive explicit **Revalidate applicability**, reviewing unchanged controlled media, prior verification and adequacy against fresh facts/evidence. It records no new physical work. Unassured work uses fresh verification/validation; negative/rejected/newer conflicting evidence cannot be revived by revalidation. Existing hard restrictions cannot be cleared here.

Private downloads and history reauthorize current facility scope on every request, including old links after revocation. Consumers see only their own safe outcome/version/time milestones and gate, with no executor, staff identity, private reason/reference/file or another owner's details. Safe error flashing retains only command UUID and permitted enums/check answers; private text, times, references, files and dependency tokens must be re-entered/reloaded. Existing error-summary focus, field associations, visible non-expiring feedback and conflict recovery are reused. UTC event entry is explicit; history shows Africa/Nairobi and distinguishes actual observation from recording. Nairobi time-entry usability remains open. No new notices, outbox deliveries, scheduler changes or external mail were introduced; unrelated historical outbox rows are retained untouched.
