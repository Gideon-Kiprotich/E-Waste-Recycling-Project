# Phase 15 design — Media and Work Correction Review

Status: **design only; implementation and proposed extensions require authorization**. Prepared 20 October 2026 after provisional Phase 14 integration at `869b479624589b10c496a2155a0d0fbe597f9d20` (implementation `9508bdbc4ff8f369549dd96452da785d2d33fccc`). No application changes, migration, operational data changes or manual acceptance accompany this design.

## 1. Authority, references and bounded increment

Established requirements: [D2](requirements/Deliverable_2_Requirements_Refinement_and_Scope_Freeze.md) FR22–FR29/FR34; BR01–BR02/BR05–BR15/BR17–BR19; [D3](requirements/Deliverable_3_Detailed_System_Modelling_and_Design.md) §2.3 UC11–UC14/UC16, §4.5, §6.6, US14/US15/US17, S10 inspection, **S11 Sanitization/work/release**, **S12 Batch/output workspace**, **S14 Exception/correction desk**, bounded S13 owned timeline; AT05–AT11, NF01/NF05–NF06/NF10–NF12. D2/D3 CR-ID-01, CR-PARTS-01, CR-MEDIA-01, CR-REUSE-01, CR-BATCH-01 including its Phase 13 extension, and CR-RESTRICTION-01 control the existing boundaries. See [C15 in the audit](requirements-completion-audit.md#c15--canonical-media-and-work-contradiction-review).

These approve immutable corrections, canonical identity, live assurance, acknowledged custody and truthful accounting, **not the detailed new recovery powers below**. C15 remains missing implementation. Proposed changes are labelled **P15**; append matching reviewed D2/D3 extensions before any later implementation, preserving every baseline entry. This document is not an approved scope-change entry or stakeholder validation.

Recommend one bounded increment: A same-identity association recording errors; B evidenced, wholly on-site HDD/SSD discovery supplements; C unchanged-configuration work/test recording errors; D erroneous unacknowledged return reports; E only the corresponding typed dependent-obligation review. Reuse the Phase 14 desk and ledgers. Do not build another exception framework or general component system.

Exclude actual replacement, re-parenting, removal/detachment commands, ownership transfer, identity merge/deletion/reissue, physical returns, redistribution, post-dispatch/loss quantity resolution, recipient succession, unsupported treatment/hazards and final project acceptance. Device re-entry remains **unresolved before final acceptance**, not implemented or authorized for deferral. A recorded observation is never a hardware operation, receipt or possession acknowledgment.

## 2. Current blockers and shared review contract

The implementation, rather than screen mockups, establishes these starting points:

- [InventoryMedia](../app/Actions/InventoryMedia.php) and [inventory SQL](../database/sql/media_inventory.sql): a bound entry can only become `disputed`; its unique canonical claim/origin remains. Unbound uncertainty can already become `not_present`. No ordinary unbinding or replacement exists.
- [DismantleBatches](../app/Actions/DismantleBatches.php) and [batch schema](../database/sql/dismantling_batches.sql): every committed input/detachment is permanent; a `discrepancy` blocks ordinary accounting and batch media authorization. [Downstream guards](../database/sql/downstream_movements.sql) already freeze movement-affecting measurements after dispatch/loss and require reservation withdrawal before pre-dispatch corrections.
- [RefurbishItems](../app/Actions/RefurbishItems.php), [reuse SQL](../database/sql/refurbishment.sql) and [reuse contract](design/phase-11-reuse-contract.md): CHANGED/UNKNOWN work configuration, unsafe/unknown test safety/configuration and owner `exception` reports remain restrictions. Ordinary genuine functional failure already has fresh-assessment recovery; it does not need a new override. An incomplete return closes its authorization as `exception`, with no partial custody transfer. Only the Consumer owner's complete exact-manifest acknowledgment records release.
- [ReviewRestrictions](../app/Actions/ReviewRestrictions.php), [effective queries](../app/Support/Restrictions/Effective.php), [restriction SQL](../database/sql/restriction_review.sql), [dependency guards](../database/sql/restriction_dependencies.sql) and the six Phase 14 forward migrations implement exact fact supersession, monotonically increasing epochs, current workflow stamps and completed-dependent holds. `restriction_dependent` currently blocks on every retained impact; C14 has no impact discharge.

For A–E use the same explicit case opening, assignment/revocation, private evidence, proposal, independent Administrator review, continue/close-without-change, event/command/outbox and recipient-only notices. Reads remain read-only. Technical author must be an active named Processor at the **actual controlling approved facility**, capable of the affected parent and media; a collection-point or pre-receipt investigation grant is insufficient. Recheck every cited technical author's scope and every affected subject's control at approval. Reviewer must be a different account from the proposal and all cited technical-finding authors, including after role changes. No new role or proxy technical signature.

Every proposal freezes exact source/event/fact, previous case/domain versions, identity/owner/control evidence, current configuration/inventory/assurance and downstream snapshot, original/proposed controlled values, observed/recorded times, reason and private attachment or accountable reference. Evidence must establish what was erroneous **then**, as well as the current situation; today's observation alone cannot establish an earlier recording error. UNKNOWN, conflicting facts or inaccessible items stay blocked. Material new facts stale a proposal, rather than broadening its approval.

Use closed, versioned evidence templates for each action. Recording-error attestations apply to A/B0/C/D; B1 uses truthful discovery/provenance/accounting attestations and E uses obligation continuity/fulfillment checks. Do not require a Processor to call a genuine discovery false, or to set C14's eight recording-error checks YES to obtain a different type of review. These typed extensions do not loosen the original C14 template.

**P15 review execution:** approval applies only enumerated typed effects backed by that proposal, atomically. Preserve the technical observer/time and separately record the approving/recording actor; do not impersonate the observer in commands/events. Where an approved correction appends a domain corrective record, a specific reciprocal review-effect reference permits that recording action only. It confers no ordinary Processor powers on an Administrator and cannot supply physical acknowledgment. No arbitrary table/field/JSON-path mutation API.

**P15 case projections:** retain C14's states/transitions for its existing contracts. New typed cases use `open → under_review`, with continued review remaining active and `closed_no_change` retaining all blockers. A/B0/C/D recording-error approval ends as `superseded`; B1 ends as `provenance_supplement_recorded`, explicitly leaving independent accounting/data gates pending. E continuity enters active `revalidation_pending`; independently evidenced fulfillment ends as `obligation_fulfilled`. Native projections must be backed by the exact permitted ledger action and active-state rule. Later proof drift shows a current blocker and requires renewed linked review; it does not edit the terminal historical outcome or mutate cases on page reads.

## 3. Action matrix

### A — Incorrect canonical-media association

**References/blocker:** FR23/FR28–FR29, BR01–BR02/BR09/BR14, UC11/UC16, S10–S11/S14, AT05/AT08/AT10–AT11; CR-MEDIA-01's deliberately retained disputed claim.

**P15 allowed actions and eligible state:**

- **A1 Confirm retained association:** an existing disputed entry actually names the correct same medium in the same unchanged parent. Verify original/current physical code, private distinguishing observations, placement, same owner and coherent facility control. Append reviewed confirmation of that binding; retain the original dispute. No new identity or placement is invented.
- **A2 Supersede erroneous association:** before parent dismantling, acknowledged return or downstream movement, prove the named canonical medium was never in that placement and no real removal/replacement occurred. Require independent valid origin/receipt and current same-owner/same-facility control for that medium, not provenance resting solely on the disputed association. First increment supports independently received standalone HDD/SSD for A2. A derived identity whose only origin is the erroneous parent stays held; reissuing it or inventing a corrected origin is excluded.

**Evidence/roles:** assigned capable Processor findings and independent Administrator approval; no physical acknowledgment occurs. Account for both parent and named medium. Serial matching alone gives no access or identity proof. Any actual wrong-owner/conflicting custody, disputed identity, destruction concern or uncertain configuration prevents positive recovery.

**Effects/invariants:** A1 adds a new confirmed binding assertion; A2 adds an `association_superseded` assertion ending only the **effective erroneous claim**. Original entry, medium ID, immutable origin, receipt, owner, custody, serial/hash, label, treatment and destruction history remain. A2 is not a detachment event and creates no replacement/alternate-parent link. Retain historical relationships for impact discovery. A partial unique constraint must enforce at most one confirmed/disputed effective claim per canonical medium; ordinary inventory commands cannot set the reviewed inactive state. Preserve old entry IDs/medium references rather than nulling them. Serial uniqueness is unchanged.

Invalidate parent and affected-medium inventory/authorization/work/release context. Require fresh physical inventory, completeness, inspection/human decision and appropriate assurance applicability review; an empty list never supplies N/A. A2 leaves parent inventory incomplete until all actual storage is evidenced through the existing observation/link workflow. Newly identified actual media still use the existing canonical identification checks. No automatic link to a different parent or automatic reuse clearance. Destruction remains permanent on its medium; this increment does not clear a parent's existing destruction/configuration concern through an association correction.

**Unsupported:** frozen batch/detachment membership changes, acknowledged manifests, physical swaps/re-parenting, sole-origin reconstruction, identity merges and unsupported-media treatment. A1 may confirm `other_nonvolatile` inventory, but treatment remains unavailable. A2 does not free an identity for a manufactured lifecycle.

### B — Unexpected medium after batch commitment

**References/blocker:** FR23–FR25/FR28–FR29, BR09–BR12/BR14, UC11/UC13–UC14/UC16, S11–S12/S14, AT08–AT11; CR-BATCH-01 permanent discrepancy and all-media obligation.

**P15 narrow eligible state:** committed `processing` batch, same original approved facility, source parent is a known permanent member, original measured input remains valid, and **no dispatch, source/downstream loss, recipient outcome or closure anywhere in the batch**. Withdraw all reservations through existing supported controls first; drafts claim nothing and become stale. Require actual observation, exact HDD/SSD kind, safe handling facts, proven source parent/accountability owner/control, identity matching and an explicit account of where its mass already sits. Unsupported/inaccessible media, unknown source/owner, external addition or conflicting custody remain discrepancies.

Freeze the observed discovery count and stable opaque references for every physically distinguished unit. One unit keeps one reference across proposals/retries; later reports must cite an existing matching unit rather than mint another identity. Unknown serials require private distinguishing observations and accountable physical-match evidence: random IDs cannot prove physical distinctness. Ambiguous count/matching remains unresolved. All reported units must be accounted for before the original discrepancy's provenance obligation can be fulfilled; approving one of several drives cannot clear the whole report.

**Actions:**

- **B0 Correct erroneous discovery report:** prove the alleged *additional* medium was a duplicate observation of an already accounted canonical drive, or an erroneous observation with no additional medium. Reference exact original production/detachment/measurement evidence. No new identity/output/quantity; no actual discovered medium may be dismissed this way.
- **B1 Record evidenced recovery supplement:** for a genuinely recovered HDD/SSD, append a separately reviewed discovery/provenance record. Recognize an eligible existing canonical identity under current authorized same-owner/control scope; otherwise create one identity with optional encrypted serial/global hash uniqueness and its ordinary QR/manual label. No serial or unknown identifier is invented. An existing identifier conflict rejects the new identity safely; do not disclose or silently adopt an unscoped match.

The supplement references batch, original discrepancy, exact source member, actual observer/time/evidence, owner/control basis and approved review. It **does not append a member or detachment to the frozen original manifest**, invent prior embedding/removal or change terminal parent state. A new subject uses the existing processor-only `processor_media` category, `processor_derived` intake class, `hdd`/`ssd` subtype, mandatory data status YES and `storage_assets` facet sharing that subject ID. Introduce explicit `batch_discovery` origin anchored to this evidenced current facility/batch observation, not an earlier first receipt or transfer. Its initial facility-control assertion has its own new observed/recorded event, not a backdated custody chain. Recognized subjects retain their original origin, owner, custody and receipts; the supplement adds no custody event for them. A drive is an output, never an additional intact input or a separately dismantled standalone drive. Exclude discovery identification/facets from first-receipt cohorts. Record the original incomplete inventory claim as historical error, never as retrospectively complete compliant work.

**Mass/stock contract:** input kg already includes the medium once. Never add its output mass as new input. Choose exactly one evidenced accounting mode:

1. **Previously unaccounted output:** explicit new canonical storage output against the supplement; retain other outputs and original input. Unknown measured output stays pending; it cannot support reconciliation/dispatch.
2. **Already included in an on-site aggregate output:** append a reviewed paired reclassification: remeasure the remaining aggregate and the separate drive, reference the old measurement/production and add one canonical storage output. Apply replacement measurements, not additive production for the retained aggregate. Both measurements/provenance and the new output are atomic. Do not both leave the drive's mass in the aggregate and count it again separately.

Do not guess which mode applies or force new totals to match old weights. Retain all original values, exact `numeric(12,3)` kg, gross/tare/net validity, observed provenance, signed variance and unchanged `max(0.100 kg, 2% of input)` tolerance. Honest imbalance is recordable and blocks reconciliation; no balancing loss/output is invented. A supplement may resolve known identity/provenance while leaving incomplete measurements or variance explicitly blocking. Unknown output mass is pending, not zero or an available quantity; measured on-site quantities do not imply future-dispatch eligibility. Unique discovery-to-medium/output associations and one production per canonical output prevent duplicate stock on retries. Mixed-owner aggregate stock has no individual owner; a supplemental drive needs its **proven** source owner and cannot acquire one by aggregate inference.

**Roles/effects/fresh steps:** capable facility Processor authors technical and measurement facts; independent Administrator reviews only that typed supplement/reclassification. No recipient receipt occurs. Approval must atomically append its exact provenance/output/corrective measurement effects or roll back all of them. Every original member/detachment remains immutable; current accounting becomes pending. Require fresh complete accounting and explicit per-medium treatment applicability after review, not automatic recovery/closure.

B0 may supersede a proven erroneous additional-media assertion. **B1 must not mark a true discovery report false:** it retains that observation and records fulfillment of its specific identity/provenance obligation through a `provenance_supplement_recorded` outcome. Separate pending measurement, reconciliation, treatment and dependent obligations continue to block their applicable steps. Reuse the existing case/evidence ledger, with this explicit typed outcome; do not force every resolution into C14's recording-error replacement value.

**P15 treatment extension:** propose authorization context **5, on-site batch-discovery HDD/SSD**, explicitly distinct from existing context 3's proven detachment and context 4's accepted downstream receipt. Require approved supplement, retained RECYCLE source decision, current coherent facility control, exact HDD/SSD capability, reviewed safety/identity and no remaining blocking obligations. Reuse `media_authorizations`, `sanitization_records`/current, separate execution/verification/validation and the unchanged method policy. An explicit applicability review can retain justified same-medium historical evidence; discovery itself proves no treatment. Do not insert a fake `batch_detachments` row to obtain context 3.

**Phase 16 dependency:** a correction affecting dispatched/lost/accepted quantities, consumed production or reservations that cannot be withdrawn genuinely depends on a reviewed downstream quantity/custody contract. Changed input mass, ambiguous mass overlap or unsupported origin also remain outside this supplement contract; unknown provenance cannot be solved by accounting alone. Even a claimed B0 error after dispatch is outside the recommended on-site-only scope: it needs evidence from the current custody/recipient chain, not necessarily a quantity adjustment. C15 records investigation and keeps such progression held. Later dispatch of discovery-origin media also remains unavailable until its downstream-origin/recipient context is explicitly extended; no context 4 detachment evidence is fabricated. B permits on-site accountability and supported treatment, not universal downstream completion.

### C — Same-configuration work/test recording error

**References/blocker:** FR22–FR23/FR28–FR29, BR07–BR09/BR14, UC12/UC16, S11/S14, AT07–AT08/AT10–AT11; CR-REUSE-01 hard safety/configuration restrictions and frozen test profile.

**P15 eligibility/evidence:** supported whole device, standalone HDD/SSD or qualifying fan in accepted current facility control, no acknowledged release/dismantling/physical change. Exact work or test record and controlled fact: misrecorded work outcome/configuration, test safety/configuration or a profile-defined functional observation. Technical evidence must prove the error at the original observation and unchanged configuration now; a successful later repair does not prove an earlier record erroneous. Current unknown or actual changed configuration remains held. Ordinary genuine failed/incomplete work/testing follows existing reassessment, without case-based conversion into success.

**Roles/effects:** assigned capable Processor and independent Administrator; no physical acknowledgment. Supersede only the evidenced controlled fact. Preserve work/test IDs, original result, answers, profile/checksum, actual-work provenance and destruction/assurance. Recompute any effective corrected test result with the original frozen profile, never a reviewer-selected PASS; **no corrected test authorizes release or substitutes for a new full test**. Ownership/custody/inventory/mass do not change.

**Fresh recovery:** advance restriction epoch, withdraw stale pending return authorizations through existing controls, record fresh inspection/human decision and live inventory/data review. Add an explicit `work_applicability` record to the existing refurbishment ledger, citing the latest actual completed unchanged-configuration work, exact correction and fresh context. This is evidence applicability, **not another physical work event**. If existing work cannot be justified, record genuine newly performed work later through the ordinary workflow. Run a new complete functional/safety profile test and obtain a new return authorization; old positive tests/approvals never revive. Support the same applicability step after A/D/E where context, rather than actual work, changed. A newer genuine work/failure record takes precedence; no fallback to older success.

**Unsupported:** actual hazard remediation/replacement, CHANGED/UNKNOWN reality, invented past work or test results, altered profiles, certification, unsupported-media capability and reversal of an acknowledged release. Current supported-method assurance remains a separate gate.

### D — Incomplete or contradictory owner-return report

**References/blocker:** FR22/FR26–FR29, BR05–BR06/BR09/BR14/BR18, UC12/UC16, S11/S13–S14, AT06/AT08/AT10–AT11; immutable owner `exception` and exact-manifest contract.

**P15 eligible recovery:** authorization is `exception`, not acknowledged; no `reuse_return_items` exist for any manifest member; same owner and exact subject set remain coherently at the original facility. Require the active original Consumer owner's explicit signed-in clarification of their own report plus independent facility observation of **every** original manifest item. Both must establish a reporting error with no actual partial handover, loss, replacement or return movement. Conflicting possession assertions stay blocked. Account/scope revocation prevents positive review, rather than allowing staff proxy acknowledgment.

**Roles:** owner can only **Clarify my return report** for their own cited exception; that narrow statement grants no staff history/evidence or case-wide mutation access. Assigned current capable Processor authors technical control/identity findings. A different Administrator approves the supported factual correction. The actual original owner must later supply the ordinary complete receipt acknowledgment; neither staff findings nor report clarification is that acknowledgment.

**Effects/fresh recovery:** supersede only the erroneous report's effective blocking assertion. Retain the report, old frozen manifest and terminal `exception` authorization; never reopen it as pending or acknowledged. Advance context, require fresh inspection/decision, work applicability or genuine new work, fresh complete tests/data gates and a **new** return authorization for the unchanged exact supported manifest. Only the later owner acknowledgment advances subject/custody versions once atomically. No mass, owner, inventory or custody changes on correction.

**Unsupported:** genuine partial delivery, owner already possesses any item despite ledger control, changed/missing manifest, unacknowledged real movement, refusal requiring physical return, inactive/unavailable owner, different recipient or acknowledged release. Those need separately authorized physical/custody recovery; they are not automatically solvable by Phase 16 quantity accounting. An already acknowledged return remains terminal and linked re-entry remains unresolved.

### E — Dependent impacts arising from A–D

**References/blocker:** FR28–FR29/FR34, BR09–BR15/BR18, UC16 alternative flow, S14 impact preview, AT08–AT11 and CR-RESTRICTION-01. The original `restriction_impacts` rows must remain immutable; merely closing a case cannot clear `restriction_dependent`.

**P15 supported obligations:** exact impacts targeting unchanged-identity sanitization evidence, unchanged-configuration refurbishment work, or preserved original on-site batch/detachment facts addressed by B. Bind the originating review/impact/target event, affected subjects, outstanding obligation and permitted fulfillment records. Processor findings and a different Administrator check the **original obligation and current facts**, not only the originating case outcome. Evidence for one impact cannot discharge another; all independent safety/data/provenance sources remain effective.

Use two stages to avoid a recovery deadlock:

1. **Review continuity; revalidation required:** the underlying factual correction advances affected authority epochs; independent continuity review attaches each typed obligation to that resulting epoch, without repeatedly invalidating its own recovery. Review the connected outstanding obligations before fulfillment. Permit only scoped investigation, actual reassessment, fresh decision/inventory, explicit evidence-applicability review and recording a fresh full functional/safety test after safe inspection/decision. These are the preparatory steps needed for revalidation, not permission for actual repair, wiping or dismantling. Actual receipt/movement, new work/treatment, release and dispatch stay blocked while the obligation is pending. For B, only its exact approved supplemental accounting effects are allowed. This does not revive old authority.
2. **Verify fulfilled obligation:** independently review exact fresh current inspection/inventory/work-basis/test or assurance validation/accounting records, identity/control, restrictions and versions. Append discharge proof for that specific impact. This consumes evidence at the already advanced epoch; it is not another fact replacement and must **not rebump the epoch**, which would invalidate its own fulfillment. Case/record versions still advance. Effective discharge is valid only while its captured dependency fingerprint/fulfillment remains current; new contradictory facts make it blocked/stale again without erasing proof.

Implement one operation-specific effective-obligation predicate in PHP/SQL, not a global `resolved=true` bypass. Fresh preparatory recovery does not authorize repair, treatment, movement or release. Any later factual correction advances the connected epoch and stales earlier fulfillment; continuity/fulfillment can be renewed against that epoch without another fact change. A changed inspection, failed/new treatment, inventory/work/control drift or another pending impact must block final progression. B fulfillment proves the supplemental identity/provenance/accounting obligation, not sanitization of newly discovered media; normal assurance gates still require later supported treatment. Historical destruction never qualifies as satisfied reusable-media evidence. E discharge itself changes no physical/terminal fact or quantity; any B measurement effect must independently satisfy B and retain original values.

**Unsupported:** impacts requiring reversal or inference of first receipt, handover, acknowledged owner return, dispatched/accepted/lost stock or closed downstream outcomes. Retain them with the exact missing recovery contract. Phase 16 may address supported downstream quantity/recipient obligations; physical returns and identity/ownership changes still require their own authorization.

## 4. Implementation boundaries and integrity

Proposed labels above must be implemented with existing Blade feedback, field-error links, focus handling and tokens; no new Stitch export or notification library is assumed. Show original → proposed → independently reviewed facts, remaining blockers and next authorized action. Explain the difference between investigation closure, fact supersession, pending revalidation and fulfilled obligation. B distinguishes provenance review from accounting reconciliation/treatment/dispatch. Consumer views show only owned safe milestones/source association, never another owner's identity, private measurements, serial, staff notes or technical evidence. Existing file/download reauthorization and private-input flashing policy remain.

Minimal forward schema/service changes:

- Add reviewed association-effect references and `association_superseded` binding state; replace the historical all-time medium-claim uniqueness with native uniqueness over effective confirmed/disputed claims. - Add an append-only `batch_media_discoveries` facet with exact review/discrepancy/source/unit/medium/output/measurement references, known-count provenance and unique approved unit/medium/production associations. - Extend batch records only with typed reviewed supplementary-output/paired-measurement effects and separate observer/reviewer provenance. Fresh completeness is mandatory; other old production/measurement semantics remain unchanged. - Add `work_applicability` to refurbishment record kinds, linked to original actual work and a current reviewed context. Update work-basis selection and test context explicitly; do not mislabel applicability as repeated work or allow an older work basis to survive newer actual work/failure. Add owner-statement references for D and an append-only typed impact-review/fulfillment facet for E, backed by existing case records. No second generic correction/event or sanitization ledger.

Use the existing transaction gate, deterministic sorted locks and route-bound command hash. Under locks recalculate the union of historical/current affected parent/media/batch/output subjects, source/case/entry/work/auth/impact and measurement versions, claims, owner/control, investigator/reviewer/owner session scope, assurance, reservations and movement state. Snapshot both sides **before** ending a false claim so invalidation cannot lose a disconnected subject. Revalidate all cited facts, exact B accounting effects and independent authors at deferred/root COMMIT. Authorized identical retries return the original result before stale-version rejection; changed payload conflicts and revoked access cannot replay private or obsolete authority. Duplicate identity/index conflicts have safe field errors; unrelated DB errors propagate. Private-file rollback removes only newly created unreferenced files.

All PHP **and SQL** gates must consume the same typed effective facts, current binding and operation-specific obligation predicates. Explicitly replace existing raw existence checks in inventory/coverage/movement, refurbishment readiness/tests/manifests, batch/discrepancy/treatment/stock and downstream blockers; keep their immutable history checks. Preparatory validation versus a new sanitization attempt, or fresh testing versus actual repair, must be distinguished at the individual command/record-kind boundary: do not loosen a generic readiness function for every operation to break a recovery deadlock. Known-definition forward patches must stop on unexpected definitions. Old workflow stamps cannot become current again. Existing C14 receipt/inspection restrictions, global identifiers, first-receipt/custody chains and terminal guards remain.

## 5. Migration and preservation strategy

No migration or DB write is performed for this design. Before later implementation, retain Phase 12–14 manifests and the **same defined 37-file scope** privately; compare it, never recapture it to conceal changes. Capture a separate guarded pre-Phase-15 baseline of all **96 current public tables**, original columns/rows, configuration/key/private files and migration status on each dedicated database. Confirm the actual expected state before writes; stop on unexpected duplicates, claim/projection/origin inconsistency or unsupported populated shapes with safe opaque counts/references, not automatic repair.

Use forward migrations only. Existing columns/records, origin identity, completed commands, events/outbox, assessment/assurance, custody, labels/routes, stock and original files must remain unchanged; default legacy contract/origin metadata does not create new technical facts or review authority. No case, discovery, release or impact discharge is backfilled. Index changes require a writer-blocking preflight and native uniqueness throughout the migration transaction. Exercise fresh and populated upgrades in isolated guarded PostgreSQL schemas, including existing disputes, standalone/derived media, detached/treated drives, terminal returns, mixed-owner stock, dispatched fractions and closed batches. Force deferred constraints before declaring success; preserve unsupported histories, rather than assuming empty fixtures. Apply dedicated DB migrations only after tests/preflight and compare before/after with the retained private verifier.

## 6. Acceptance and verification contract for later implementation

- **MC01 association recovery:** A1/A2 → fresh inventory/assessment/decision → explicit assurance/work applicability → new full test/eligible next action. Deny sole-origin ambiguity, wrong owner/control, unsupported scope, destruction, completed batch/return and actual physical change. Prove effective claim exclusivity, historic relationship retention and unchanged identities/custody/receipts.
- **MC02 unexpected media:** B0 no duplicate output; B1 new/recognized canonical HDD/SSD, unknown serials, duplicate identifier rejection, legitimate current-facility provenance, missing source/owner evidence, both mass-accounting modes, pending measurements, honest variance and exact tolerance. Preserve original membership/detachments/input mass, one output/stock quantity, mixed-owner privacy and unchanged existing media. Reject dispatch/loss/closure and reservation races; context 5 requires explicit supported assurance, never fake context 3/4 or universal treatment.
- **MC03 work recovery:** each supported profile; original then/current recording error versus genuine failure/configuration change; independent approval → fresh inspection/decision → applicability of retained actual work → new full test → fresh return authorization. Prove no old pass revival, no invented repair, newer failure precedence and unsupported-media/destruction blocks.
- **MC04 return recovery:** erroneous owner report + original-owner clarification + all-item facility evidence → independent review → fresh prerequisites/new exact authorization → **actual owner's later acknowledgment**. Prove correction alone changes no custody, old exception/authorization stays terminal, receipt is once-only and atomic. Deny proxy owner, partial/unknown possession, altered manifest, revocation and acknowledged-release reversal.
- **MC05 dependent obligations:** exact supported impact review, preparatory recovery without gate bypass, independently verified fulfillment and reblocking on new facts. Test multiple/independent impacts, stale fulfillment, unchanged completed work and assurance/destruction. Prove no circular requirement to obtain a prohibited physical outcome before preparatory review; no epoch bump invalidates its own fresh fulfillment. Unsupported physical/downstream impacts remain visible and blocked.
- **MC06 native integrity:** real competing association reviews, canonical identification, supplement/output creation, paired measurements, downstream reservations, owner acknowledgment and impact discharge; stale/changed versus identical commands, revoked staff/reviewer/owner/evidence links, direct invalid writes, forced deferred constraints and actual root-COMMIT failure with ledger/stock/custody/file rollback. Check each path on fresh/populated upgrades and repeat preservation comparisons. No tests access development or substitute SQLite.
- Run full PHP/PostgreSQL after application changes, final affected coverage after localized fixes, Pint, build, relevant HTTP and JavaScript checks, applicable Composer/platform validation. Record every actual result/failure; preserve benchmark targets and the historical **15.0599 s / 15.06 s** routing failure against unchanged **10 s**, plus simulation/evaluation qualifications.
