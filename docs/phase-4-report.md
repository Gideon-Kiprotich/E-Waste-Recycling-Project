## Requirements and decisions recorded before implementation

Reviewed D2 FR02–FR04, FR07–FR09, FR28/FR34, BR02–BR05/BR14/BR17/BR19/BR20; D3 US02, UC02/UC06, §§3.3/4.5–4.7/5.4–5.5, S05/S06, AT02/AT11; CR-ID-01 and CR-PARTS-01; the Phase 3 directory/eligibility/versioning implementation. Reviewed the original local S05/S06 Stitch HTML and screen images. Existing cards/tokens/form/feedback/pagination conventions are reused. Prototype certification, hazardous-dispatch assurances, invented contacts, assignment controls and SLA claims are omitted.

D2/D3 require review before assignment but do not define a separate request-review state machine. The smallest compatible implementation decision is an additional review projection, separate from the existing outcome-derived request header: `pending`, `ready`, `hold`, `stale`. An Administrator may record **Ready for later allocation** only when all current eligibility checks pass, or an explained **Hold**. A hold preserves reservations. There is no new rejection/cancellation transition, generic safety override, appointment, assignment, receipt or custody transfer. Unknown/declared safety and fan uncertainty remain blocking for a ready decision; specialist resolution remains deferred. Data-bearing YES does not itself block collection review or imply sanitization.

Existing organizations/places remain the directory entities. Organization `approved` is presented as active/reviewed within the project, never regulator certification; pending/suspended and legacy rejected statuses remain distinct. Places include collection points, facilities and depots; only active reviewed **collection points** enter the existing public/drop-off selection. Capabilities always name exact supported category/subtype pairs on each linked place, including each HDD/SSD/fan and router/keyboard. Organization capability comes from its places, not a second category registry: pickup readiness requires a reviewed collector with an active compatible place, and a compatible receiving place operated by a reviewed processor/both organization. Facilities/depots remain scoped configuration, not implemented receiving/assignment workflows. Synthetic identity markers are permanent; new records explicitly declare their synthetic status and changes cannot convert existing demo data into real operators.

New management writes require contact details, a reason, expected versions and command keys. Missing review evidence keeps records pending; activation requires retained private evidence and reviewed organization eligibility. Development currently has two Consumer memberships and no Administrator. The minimal authorization linkage is a local-only, interactive first-Administrator bootstrap command: hidden password/confirmation, dedicated non-elevated database guard, unique new email and atomic user/membership creation. It refuses existing-account conversion and further provisioning when an active Administrator exists. It is not run against development during implementation; full staff provisioning remains deferred. Administrator access uses existing active membership/session guards on every route and again within mutations.

Directory changes conservatively invalidate review of outstanding requests, including pickup requests that have not yet selected a downstream operator. Observation/date/cancellation changes invalidate prior decisions through the existing request version. Request review snapshots store evaluated request, observation, point/operator, capability and service-area versions without copying contact/address/identifiers into audit metadata. Administrator history exposes retained versions/configuration; Phase 3 did not snapshot directory versions at submission, so no missing historical configuration is invented. Private notes/contact and directory revision snapshots are encrypted. Consumer projections contain only controlled status/guidance and never staff notes or evidence.

## Implementation and integrity

A forward migration extends the existing organizations/places with version, encrypted contact and reviewer metadata; retains legacy rejected states; adds suspended states and facility/depot kinds; adds encrypted `directory_revisions` and append-only `request_reviews`; and adds the separate review projection/FK/index to requests. Existing event, command, outbox and attachment/evidence infrastructure is reused. Old device links retain their subject references; management evidence has an allowlisted organization/place/review target validated against its event. History/link triggers prevent destructive edits, synthetic/code/organization identity is permanent, and the review projection must match its evaluated request version. Existing identity, storage-facet, reservation and history constraints remain enabled. No historical migration is rewritten.

All relevant service mutations enter one PostgreSQL transaction advisory gate before actor/subject/request/directory locks. This deliberately serializes directory/review/request/observation mutations in the bounded prototype to avoid lock-order inversions and stale configuration races. Administrator actor/session/membership and request owner account/membership are rechecked under locks; existing subject ordering and retry-first contracts remain. The gate is a throughput limitation to reconsider with measured needs in a later design, not an unproven performance claim. Directory changes append request revalidation events and advance versions conservatively for all outstanding work. Observation/date/cancellation version changes make prior reviews stale. Read-time snapshot comparison also detects out-of-band account/service-area/configuration changes; any future allocation must revalidate current facts rather than trust a stored ready flag.

Management evidence uses a separate non-public private disk. JPEG/PNG reuse GD re-encoding and 16-megapixel limits; PDF content/MIME/size checks reject obvious active/disguised content and downloads use attachment disposition, no-store, nosniff and a restrictive sandbox policy. All evidence is at most 5 MiB. PDF parsing/malware scanning and professional document trust are not claimed. Failed transactions compensate newly written blobs; retries compare the original file checksum and do not duplicate attachments. Contact/notes/coordinates/uploads and protected fields are excluded from flashed input; safe permitted fields remain.

## Manual acceptance and operational limits

1. Privately run `php artisan app:create-initial-administrator` locally if needed, choosing a new account/password at the terminal prompts. Sign in and confirm existing Consumer accounts retain access. No password should enter chat, command arguments or reports.
2. With synthetic records, create an operator and point/facility/depot; record exact loose-drive/fan/peripheral capabilities, truthful hours/contact/location and private JPEG/PNG/PDF evidence. Confirm pending evidence, reviewed activation, invalid file/input feedback, synthetic permanence and retained configuration history.
3. Review owned mixed-device/part pickup/drop-off requests. Confirm current observations/preferences/estimated mass, private location/contact and evaluated versions; safe ready status; and mandatory holds for safety/unknown/fan restrictions or incompatible/unavailable directory entries. No booking, receipt or custody change should appear.
4. Suspend an operator, close a point or remove a subtype; revise an observation or date; use stale/duplicate forms in two Administrator sessions. Confirm fresh review is required, reservations/history remain, and Consumers see only safe guidance without staff notes/evidence.
5. Complete full keyboard tasks and screen-reader announcements/associations, including pagination/history/evidence/error states, on desktop and 360px. Check actual contrast, mobile touch/scrolling and long values. These user acceptance checks remain unperformed/unverified by this report.
