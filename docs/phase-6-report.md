## Implementation decisions

- Administrator vehicle declarations use existing role/session checks, command hashes, retry-first results, versions and append-only domain events. Codes/operator/classification are permanent; capacity, maximum duration, Collector mapping and declared availability are revised with optimistic versions. This is not a calendar or general fleet-management module. All directory setup must finish before renewed Ready review and Collector acknowledgment. Vehicle edits invalidate route approvals only, preserving those request/assignment prerequisites.
- Freeze validates operator/depot/vehicle setup and captures currently eligible Accepted pickups through the existing assignment eligibility service. Outstanding request items aggregate to one stop with positive summed estimated kg; no storage join doubles a drive. Offered/changed/ineligible jobs are retained as concrete exclusions with recovery links. No development record is repaired, offered, accepted or otherwise made eligible automatically.
- Frozen inputs include source versions/dependency fingerprints, submission time, assignment/request/receiving references, coordinates, mass/service time, depot/vehicle/Collector facts, mode/profile and matrix. Coordinates, matrices and dependency evidence live in an encrypted snapshot; no contact/address/serial snapshot is copied. The snapshot comparison key is keyed. Public event payloads contain only safe IDs/counts/source; command hashing conventions are retained.
- The short capture transaction releases its gate/locks before matrix construction and PHP calculation. Results may be retained if source facts subsequently change, but approval transactionally locks dependency rows in stable order and recaptures eligibility before claiming resources. GET requests never repair stale projections, append events or acquire approval claims.
- Both algorithms use the identical frozen input and stable vehicle order. Baseline chooses submission time then stable job ID among feasible append candidates; proposed chooses nearest reachable feasible append then ID. Capacity is cumulative picked-up mass; travel plus stop service and depot return must fit duration. Assignment Collector must match the route/vehicle Collector. No reload tours, intermediate unloading, facility delivery or receipt is inferred from depot return.
- Proposed tours use stable first-improvement 2-opt with full directed-tour recalculation, preserving served jobs and feasibility. Stop at 100 improving iterations/tour or the ten-second shared local computation deadline; preserve the last validated feasible result and expose exhaustion instead of claiming convergence. Independent output validation checks route/Collector uniqueness, mass/time/return, metrics and complete served/unserved accounting. Unreachable edges are never replaced with zero. Coverage differences and zero baseline distance suppress percentage improvement; zero/negative gains remain reportable.
- Comparison inputs/results, route/stop projections and dependency references are retained immutably. A comparison can be approved once; rerunning creates a new comparison. Proposed-plan approval exclusively claims served assignments, vehicles and Collectors until Stale, Superseded or Withdrawn. These are bounded prototype claims without a time slot or automatic completion. Explicit supersession closes one selected same-operator approval atomically; other conflicts roll back. Neither route claims nor their release alter item reservations, accepted assignments or custody.
- Database dependency triggers stale affected approved plans, release all their route claims and append a safe approval-history cause on relevant record changes. Whole-plan invalidation is deliberately conservative. Source drift is also checked before actionable/Collector reads, including elapsed eligibility, without GET writes. Existing request cancellation releases only its selected item reservations; replanning requires the existing review/reoffer/reacknowledgment workflow where applicable. History retains old proposals, approvals and invalidation reasons.
- Named Collectors see only their current approved ordered tour and links to existing independently authorized accepted-job details. Route pages never copy contact/address fields or expose another Collector's tour. Existing Consumer milestones and Processor boundaries remain. Pages are private/no-store with no-referrer metadata; precise locations never enter URLs or persistent browser storage.
- Optional route maps reuse installed Leaflet and existing `maps` configuration/attribution. They load only after **Show simulated map**, send no names/contact/address/request reference to tiles, and display straight-line simulation rather than navigation. Scroll-wheel zoom is disabled; mobile map dragging/touch zoom are disabled so the ordered list stays usable. Disabled/import/tile failures leave that complete list available. No route calculation depends on map access. Browser visual/accessibility behavior is not established by HTML/JavaScript assertions.
- Privacy notice `2026-10-15.1` explains accepted-assignment access, encrypted routing snapshots and optional route tiles, correcting the earlier pre-assignment wording. Previous notice files and acknowledgment records remain unchanged. Form errors reuse focused summaries and input/group associations, preserving only allowlisted fields and bounded opaque selection references. Passwords, coordinates, private reasons and forged fields are never flashed. Checkbox markup reuses the existing acknowledgment styling instead of inheriting full-width text-input controls.
