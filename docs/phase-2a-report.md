## Implementation decisions and requirement traceability

- **PI01 / bounded vocabulary:** `Questions` supplies exact category/subtype labels and `PARTS-SELF-REPORT-1.0`. A fan is one dedicated ICT cooling fan/blower up to 24 V DC and 140 mm across its housing, excluding free leads. Initial registration requires scope YES; BASIC or UNKNOWN electronics are allowed, while scope NO/UNKNOWN and known ADDITIONAL electronics receive the specification's exact field errors. Ordinary motor-driver/tach/PWM circuitry is basic. Unsupported/ambiguous GET selections show guidance without loading an incompatible registration form.
- **PI02 / observations:** HDD, SSD and fan have their specified separate required scalar keys/vocabularies; extra, missing, nested and N/A answers fail. Functional questions concern previous use only. Common damage/safety declarations retain Unknown; notes remain required. Guidance never requires powering, dismantling or internal inspection. Existing `SELF-REPORT-1.0` is frozen; history resolves each observation's stored version. Fan revisions may honestly record later NO/UNKNOWN eligibility or ADDITIONAL/UNKNOWN electronics, retaining all earlier versions and displaying review guidance.
- **PI03 / authoritative metadata:** the action derives immutable `items.intake_class` after successful-retry resolution. HDD/SSD always project and snapshot data-bearing YES on create/revise, including unknown/erased/broken declarations. Consumer data-status overrides fail even if YES or null. Eligible/basic fan self-report derives NO; other recorded fan combinations derive UNKNOWN, with no technician approval. Every standalone drive has exactly one `storage_assets(subject_id, media_kind)` facet sharing its existing subject/item UUID and matching its subtype. Fans/old devices have no facet. There is no extra identity, owner, code, custody, data-status copy or parent/removal record.
- **PI04 / identity and retries:** unchanged encrypted identifiers, context-separated comparison/command hashing and `app-key-context-1`; global partial unique `items_identifier_hmac_unique`. Normalization trims, removes whitespace and ASCII hyphens, uppercases ASCII letters and preserves leading zeroes. Namespace spans owners/categories/manufacturers, serial/IMEI and key-version labels; optional/empty/separator-only identifiers remain null and do not conflict. Parts accept Serial only (omitted kind retains existing Serial interpretation); explicit IMEI, including blank identifier, fails. Old device IMEI format/checksum behavior remains. Numeric part serials share the IMEI namespace. Duplicate error remains “This serial/IMEI is already registered. Please recheck the number entered.” No matched owner/item/code is disclosed. Legacy command bytes receive no injected kind/default/derived fields before hashing; both pre-upgrade registration and revision retries are exercised with frozen canonical payload fixtures. New same-command retries return the original identity/facet/history/photo; changed payload conflicts, a genuinely new duplicate command fails.
- **PI05 / origin and protected fields:** parts use explicit registration/revision top-level allowlists, plus exact answer schemas. Protected parent/origin/storage/identity/custody/status/quantity and other unknown fields fail by presence, including null and arrays. Existing consumer-device requests also reject parent/origin fields. No parent lookup or processor provenance endpoint was introduced. Validation failures flash only typed permitted fields, a valid submission reference and applicable version; private identifiers/photos, framework tokens, passwords, protected fields and malformed values are excluded.
- **PI06 / atomicity:** reuse `RegisterDevice`, its actor/category/subject locks, global comparison advisory lock, existing transaction, private-photo re-encoding and compensation. Facet insertion occurs inside the same registration transaction before observation/event/custody/outbox/photo completion. Specific named uniqueness conflicts become the private field error; unrelated database failures are retained as failures. Tests inject failures at facet/event/custody/photo-link boundaries and a named conflict after photo storage, proving zero partial linked records or private blobs.
- **PI07 / access:** reuse current-account/session middleware, Consumer role and owned queries/policy. Other consumers get private 404; staff roles remain denied; guests redirect; suspended/stale sessions fail. Existing CSRF/authentication/recovery security tests remain intact. Facets are metadata on the same owned item, with no independent/public route. QR continues to encode only the authenticated opaque lookup reference.
- **PI09 / feedback and views:** reuse Blade feedback/components, project CSS tokens/layouts and upload/QR services. Friendly part labels, origin and storage/data obligations appear in owned views/history/print. No parent/removal or collection/treatment event is fabricated. Private input is blank after rejection, safe values persist, output is escaped, field errors use `aria-describedby`/`aria-invalid`, and one error summary links to fields or the focusable heading for forged fields. Minimal existing JavaScript explicitly focuses summary-link targets. Existing responsive CSS remains unchanged; actual visual/keyboard/screen-reader acceptance is separate below.

Key implementation files: `app/Support/Devices/{Questions,SafeInput}.php`, device form requests, `app/Actions/RegisterDevice.php`, `app/Models/{Item,StorageAsset}.php`, `DeviceController`, scoped validation rendering in `bootstrap/app.php`, device Blade views/shared summary/layout and minimal focus JavaScript. No dependency, lockfile, identifier service, auth policy/middleware, test guard, historical migration or reviewed design asset was changed. README now explains bounded parts use and forward migration behavior.

## Forward migration and preservation

`2026_10_06_000001_create_standalone_parts_intake` is forward-only and transactional. It locks category/subject/item writes, then checks expected category versions/labels, legacy item category/subtype shapes, exact existing identity/history functions, enabled triggers, global unique index and old subtype constraint before mutation. Unexpected state aborts with a safe message rather than guessing or editing identifiers. Destructive rollback is refused.

Upgrade adds immutable classification, backfilling existing rows to `whole_device` only, and creates the empty same-ID storage facet table. Classification/category/subtype agreement and drive YES are persistence guards. Facet PK/FK (subject deletion RESTRICT), media CHECK, immutable update/delete guard and two initially deferred reciprocal constraint triggers require one matching facet for a standalone drive and forbid missing/mismatched/non-drive/orphan facets at transaction enforcement. Existing identity/history/identifier-kind protections remain enabled; no maintenance exception or weakened production protection was required.

The historical device migration imports the live `Questions::CATEGORIES`. On a fresh installation it therefore seeds the new category with the old question version. The forward migration accepts only this exact known seed, preserves its UUID and corrects its version to `PARTS-SELF-REPORT-1.0`; an upgrade without that seed inserts it once. `Questions::VERSION` and all historical migration files are unchanged. Private-schema tests run all historical migrations, then exercise both the fresh-seeded and populated six-category upgrade paths, unexpected seed/disabled-guard/legacy-row aborts and refused rollback. Each schema and all fixtures roll back; teardown verifies its disappearance. No database was reset.
