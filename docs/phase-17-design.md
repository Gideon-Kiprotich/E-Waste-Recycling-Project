## 3. One reporting basis and explicit scope

**Basis:** current effective facts and current qualification of outcomes, evaluated once at `generated_at_utc`, for a visibly named original cohort. Period means cohort-entry period, not when every later outcome happened. A late correction can change the current result for an older cohort; show its new revision/reference and original facts. Do not offer an arbitrary `as_of` parameter or reconstruct past database state. Exporting the current evaluated snapshot is not such an engine.

Defaults: last **30 Africa/Nairobi calendar days including today**, date-only inclusive From/To, at most **366 days**, supported category/subtype All, authorized facilities All for Administrator and the current facility for Processor, 25 rows/page, stable tie-break ID. Reject unauthorized/unknown filters before querying; do not silently broaden them or return unauthorized zero totals. Convert period to `[local From 00:00, local day-after-To 00:00)` UTC. Fixed views are **Collections**, **Facility cohort**, **Batch accounting** and **Collector manifest**. Every card/CSV names its date field; live work cards explicitly ignore report-period controls. No default comparison period or optional analytics.

Identity/cohort definitions:

- **Consumer-origin subject:** `items.intake_class IN ('whole_device','standalone_part')`, counted by `subjects.id`, separated by intake class/category/subtype. A same-ID `storage_assets` facet is never a second subject. `processor_derived`, discovered media, detachments, outputs and lots never become new Consumer collections. A recognized discovery keeps its genuine original identity/origin; discovery does not count its older first receipt again.
- **Collection cohort:** one actual `first_receipts` row per Consumer-origin subject, with its real `first_receipt` event/observed instant. Registration, requests, visits without an accepted subject, repeated transfers, reservations and scans add zero. Attribute collection facility to the actual receiving place if applicable; Collector receipt can have **No receiving place at first receipt**, not the proposed destination. Current custody is not the cohort attribution.
- **Facility cohort:** the first actual admission of that Consumer-origin subject to **any processing facility** (`places.kind='facility'`), from an evidenced accepted custody chain. Follow `first_receipts`/`handover_receipts` and recipient party/event ancestry in custody-version order; never infer admission from an offer, intended destination, assessment, or a current role. Collection-point receipt alone does not qualify. Count a subject once globally, attribute it to its first processing facility and use that admission's observed date. Later facility transfers add zero. This is an origin cohort followed to its current outcome, **not a productivity score for whichever facility later performs work**. If legacy evidence cannot establish the first eligible admission, show an unclassifiable count; do not guess from a current place classification or timestamp minimum.
- **Batch cohort:** original actual `batch_commit` observed date and immutable source facility, one batch ID. Effective input/output measurements change values, not original membership or cohort dates. An output media measurement is part of output balance and never another batch input. Category filtering includes a batch's mass only when **all original inputs** match; show the excluded mixed-category batch count separately. Never allocate its mass proportionally to selected devices/owners. Output type/material filters are fixed details within Batch accounting, not arbitrary formulas.

Authorization is applied before aggregation and after following lineage. Consumer gets owned status/counts and own estimate only, no staff CSV, batch kg, other owners, private identifiers/contact/evidence or derived recovery percentages. Collector gets current personally assigned work and its manifest only, no facility/global mass or release rates. Current eligible Processor gets its own facility's source batches and first-facility cohorts, plus its personally authorized destination shipment slices in a separately labelled non-additive incoming view; no whole source-batch totals from receiving one slice. Administrator gets system aggregate/report rows and oversight counts under current active role, not automatic access to serials, evidence or mixed-owner private timelines. Private case access still requires existing explicit case scope.

Proposed report permission permits **safe aggregate current outcomes of an authorized first-facility cohort after later transfers**; it never grants the originating staff destination evidence or general cross-facility item access. Export/detail links reauthorize independently. Unsupported supplied owner/organization/serial filters are rejected. No persistent dashboard-result cache initially; all responses are private/no-store. Authentication, scope/version and redaction changes invalidate old snapshot/export authority, including after role restoration.

## 4. Fixed metric catalogue

All metrics inherit §3 scope, generated time, definition version `C17-1.0` and correction references. Show original and current effective quantity columns where changed, plus original record and current review reference to authorized staff. Opaque report revision identifies the exact scoped membership, source versions, effective revision vectors, obligations and privacy state; a bare maximum event/version is insufficient. Nullable kg stay unknown. Sum known values with known/eligible coverage and unknown counts, never `COALESCE` a missing observation to a reported zero. Totals use integer grams/PostgreSQL numeric; format kg to three decimals. Compute rates from integer counts, round only displayed percentage to two decimals, and never average subgroup percentages. For non-rate metrics numerator/denominator is **not applicable**.

### R01 — Items first received from owners

- Meaning/source/effect: distinct actual Consumer-origin `first_receipts.subject_id` joined to its physical event and original request item; first physical acceptance remains historical. C14 corrections of refusal/safety observations cannot invent or remove an actual receipt. Add a current exception badge without rewriting that receipt.
- Unit/grain/formula: physical subjects, one subject; `COUNT(DISTINCT subject_id)`. Separate whole-device and standalone-part/subtype counts; facet joins use existence/distinct identity, not row counts.
- Date/types/filters: Collection cohort observed date, supported Consumer-origin categories only; exclude no-receipt registrations, all derived/discovered outputs, visits and later handovers. Facility filter is **actual first receiving place**, including explicit No receiving place; not first processing facility.
- Roles/empty/unknown: owned Consumer count, Administrator aggregate; Processor only its authorized actual-receiving-place subset, labelled accordingly. Collector's work does not grant this report. Empty is 0; broken/missing ancestry is separately unclassifiable, never an extra collection.
- Independent oracle: F-C gives **8 = 7 whole + 1 standalone HDD**, despite repeated handovers, two extra processor-origin media and a storage facet. Boundary C09 and unreceived C10 contribute zero.

### R02 — First processing-facility cohort size

- Meaning/source/effect: subjects with first evidenced processing-facility admission per §3. Reuse real physical receipt/event/party chains; later custody, recognized discovery and current recipient succession do not create another admission.
- Unit/grain/formula: unique Consumer-origin physical subjects, one first-facility admission per subject; distinct count, no denominator.
- Date/types/filters: first eligible admission observed date and original first facility; same category/intake-class splits as R01. Include later released/dismantled/exception subjects in the denominator; exclude derived media, collection-point-only subjects and unknown admission evidence.
- Roles/empty/unknown: Administrator and current Processor for its first-facility cohort. Consumer sees owned admission milestones, not this facility total; Collector excluded. Empty is 0 and missing classification separately disclosed. A later transfer to B never shifts A's cohort to B.
- Independent oracle: F-C gives **6 at A, 0 new at B**, even though C01 later passed through B; C07/C08 remain at collection point. Denominator remains 6 after later outcomes/corrections.

### R03 — Current acknowledged reuse-return rate for the facility cohort

- Meaning/source/effect: current supported recorded reuse-return outcome among R02 subjects; never a recommendation, passed test or pending release authorization. Require matching `reuse_authorizations`, `reuse_manifest`, `refurbishment_records(kind='acknowledge')`, `reuse_return_items` and actual `reuse_returned` event for that original cohort subject. Embedded/derived manifest members do not enlarge the denominator/numerator. Apply current effective corrections and exact unresolved obligations; retain original acknowledgment as historical even when current qualification is disputed.
- Unit/grain/formula: subjects and percentage; numerator = distinct R02 subjects with evidenced actual acknowledged reuse return and no current contradictory outcome/obligation; denominator = all R02 subjects. Also show historical acknowledged count and current partition: qualified reuse return, batch-linked awaiting/final recorded outcome, other pending, current exception. Exception takes precedence for the current partition; historical facts are annotations, not a second current bucket.
- Date/types/filters: R02 admission cohort; later valid outcome can fall outside selected dates, evaluated at generation. Eligible whole/standalone original subjects only. No release-date-period rate. Follow safe aggregate current outcome across transfers as explicitly proposed in §3.
- Roles/empty/unknown: Administrator/current source-cohort Processor only. Zero denominator gives **Not applicable (0 received)**. Pending, unverified, unsupported and disputed subjects stay in the denominator and outside numerator, with incomplete counts. Do not call them failed reuse. Do not use pre-release action-readiness predicates after actual owner receipt: changed custody is then expected, not proof release never occurred. A small read adapter must evaluate the terminal record and current contradictions without changing operational guards.
- Independent oracle: F-C denominator **6**, current qualified **2**, displayed **33.33%**, historical acknowledged **3**. C06's later exception is visible; two batch-linked pending, one other pending and one exception give **4 incomplete current outcomes**, not 0 or a 50% current release claim.

### R04 — Estimated mass of the collection cohort

- Meaning/source/effect: original requester estimate tied to R01's accepted request item/frozen receipt context. Existing `request_items.estimated_kg` is required, positive and immutable; use that exact original row, never a latest self-report or substituted measured batch/receipt weight. Later measured corrections do not change this estimate column. Do not add nullable estimates or fabricate such request rows for reporting tests.
- Unit/grain/formula: estimated kg per original R01 subject, summed once; known-estimate count / R01 count is an explicit coverage ratio, not an estimated recovery rate.
- Date/types/filters: same R01 cohort and first-receiving-place/category filters; no detached/discovered/facet contribution or parent-plus-child double mass.
- Roles/empty/unknown: Consumer own estimates and Administrator/authorized receiving-place Processor scope as R01. Empty cohort = known sum 0.000, coverage 0/0 **Not applicable**. Legitimate current-schema receipts have a known original estimate; missing/broken ancestry is an integrity/unclassifiable result that prevents a complete export, never a manufactured null/zero estimate. Test that defensive read boundary without weakening native non-null/positive constraints.
- Independent oracle: F-C estimates `2,3,4,5,6,7,8,0.500` kg yield **35.500 estimated kg, 8/8 known**. Measured facts in F-B cannot alter this value. Unknown measured observations are exercised separately by valid F-B2, not by an impossible request estimate.

### R05 — Measured batch input, produced output and variance

- Meaning/source/effect: for each Batch cohort batch, original committed input membership plus current `downstream_effective_measurements` at its existing input/output measurement anchors. Count every original `batch_outputs.subject_id` once, including measured canonical storage output; reuse `batch_balance`'s effective definitions and existing tolerance `max(0.100 kg, 2% of effective input)`. Original measurements remain alongside revisions.
- Unit/grain/formula: kg per batch; input, sum produced outputs, variance = input minus outputs. Aggregate known input/output separately with independent coverage; **do not sum batch tolerances or claim offsetting variances reconcile separate batches**. No denominator except disclosed measured/eligible counts.
- Date/types/filters: Batch cohort commit date/source facility, all original input categories matching §3; include historical closed batches and current exceptions. Never blend with R04 estimates or Consumer per-device mass.
- Roles/empty/unknown: Administrator/source-facility Processor; recipient sees its authorized slice, not this full metric. Unknown input/output makes that batch's variance **Pending measurement**, not 0.000; imbalance remains visible and blocking. Empty = no batches, sums 0.000 with zero coverage.
- Independent oracle: F-B1 original input/output **10.100/10.100**, effective **10.000/10.000**, variance **0.000**, tolerance **0.200** with D review references. F-B2 has known input 5.000, measured output 4.800 plus an unmeasured output: variance pending. F-B3 `2.000−3.000 = −1.000` remains an exception; no loss/adjustment lot repairs it.

### R06 — Effective source stock and reservations

- Meaning/source/effect: use shared `downstream_stock(output)` / effective records, not raw sums or a new production ledger. The same production's reviewed facts can change its numbers; review does not physically return stock.
- Unit/grain/formula: kg per original output then source batch; `A=P−D−Ls`, `V=A−R`, with produced P, dispatched D, source loss Ls, outstanding reserved R, source quantity A and unreserved V shown separately. Downstream acknowledgment/completion/transit/post-acceptance loss deduct source **zero additional times**. No rate denominator.
- Date/types/filters: Batch cohort/source facility and allowed output/material filter; all output types, separate canonical storage from aggregate material/component/residue. These are current stocks of the selected original batches, **not stock movements during the date period**. Historical-closed residual V is labelled blocked for new movement.
- Roles/empty/unknown: Administrator/source Processor only; incoming recipient slice never grants source stock access. Known zero differs from unmeasured P; partial aggregates carry unknown-output counts. Nonnegative/conservation failures are report integrity errors, not clipped zeros.
- Independent oracle: F-B1 effective **P10.000, D8.000, Ls2.000, R0.000, A0.000, V0.000**. The accepted/completed/lost downstream slices do not turn A negative or restock it. A separate reserve 3.000 → withdraw 1.000 → dispatch 2.000 on P5.000 gives R0.000, A/V3.000, not A2.000 or V5.000.

### R07 — Recorded downstream allocations and outcomes

- Meaning/source/effect: disjoint current dispatch and accepted-slice partitions from effective records, original ancestry and current evidence/obligation qualification. Reuse P16 remaining/quantity functions; never add dispatch and acceptance as two material streams. Genuine completed history followed by later incidents remains history plus a current exception; a reviewed false completion becomes ineffective/pending under its existing revision.
- Unit/grain/formula: kg per original dispatch/acceptance/output, roll up once per batch. Dispatch = accepted + refused + shortage + disputed + confirmed transit loss + unreported. Acceptance = recovered + disposed + controlled storage + confirmed post-acceptance loss + pending. Loss summary = source + transit + post-acceptance, distinct from recovered. Show recorded-effective outcome kg, currently qualified kg and disputed kg separately; stale proof cannot be promoted to a currently qualified recovery total or silently erased. No optional recovery percentage.
- Date/types/filters: Batch cohort/source facility, output/material filters, not completion-date flow. Source staff get authorized outcomes; destination staff only personally authorized shipment slices. Storage completion is supported controlled storage only; material/components recovered/disposed, residue disposed. Unsupported/unknown paths are pending.
- Roles/empty/unknown: Administrator and the stated scoped Processors; no Collector or Consumer batch mass/yields. Empty = no allocations. Missing kg/evidence is unknown/pending, never a zero terminal outcome; report current restrictions separately from immutable quantities so conservation still reconciles.
- Independent oracle: F-B1 accepted **6.500**, recovered **4.000**, disposed **1.500**, storage **0.500**, transit loss **1.500**, accepted loss **0.500**, source loss **2.000**, pending/unreported **0.000**. Total lost **4.000**, not recovered 8.000. `4+1.5+0.5+4 = 10`. Original recovered **4.100** remains visible with its correction reference.

### R08 — Historical closure and current batch exceptions

- Meaning/source/effect: count immutable original close records and current `downstream_status`, `batch_balance`, effective restrictions and exact dependent-obligation predicates. A closed case, old close or fulfilled historical obligation is not current clearance by itself.
- Unit/grain/formula: distinct batches; a current partition into open, closed recorded outcomes, closed with loss, closed reviewed accounting, closed later evidence exception. Historical closed count is a separate overlapping annotation, never added to the partition. Current blocker reason counts can overlap and are explicitly non-additive. No denominator/rate.
- Date/types/filters: Batch cohort commit date and original source facility/category rule, including later contradictions regardless of contradiction date. Keep original close time/reference and latest review time/reference.
- Roles/empty/unknown: Administrator/source-facility Processor; owner only safe linked status, no cohort totals. Empty = 0. Unknown/incomplete proof remains open/exception, no second close or inferred physical completion.
- Independent oracle: F-B's four batches give historical closed **2**, current closed-with-loss **1**, later-evidence-exception **1**, open **2**, ordinary/reviewed closed **0**; current partition sums to **4**, not 6. F-B4's historical close remains visible when its newer obligation is unfulfilled.

### R09 — Live role work counters

- Meaning/source/effect: current attention/work references from existing scoped queues, role eligibility, effective restrictions and current authority; links perform no new operation. Count each reference once despite joined event/evidence rows. Readiness stays subordinate to existing command gates.
- Unit/grain: Consumer = requests with outstanding active request items; Collector = current personally offered/accepted assignments split by state, each assignment once; Processor = distinct currently scoped nonterminal physical subjects in the relevant intake/assessment/media contexts, split Consumer-origin/processor-origin; Administrator = active open/under-review/revalidation-pending restriction cases. Actual blocked work remains listed with its supported next-step link.
- Roles/empty/unknown: respective role only; revoked/ineligible work exposes no details. Empty authorized queue = 0 and existing setup guidance; denied scope is not a zero report. Current unknown readiness shows Needs review rather than an enabled action.

## 6. Consolidated timeline and lineage

Propose one paginated **Item timeline** and one **Notifications** inbox; preserve existing stage URLs and use them for permitted next actions/evidence. Reuse Context scope/labels, existing safe stage projections and Blade cards rather than dumping `domain_events.safe_payload` or inventing a parallel state machine. Extract small shared presenters only for the existing repeated safe formatting.

Anchor the graph in the authorized subject/request, then follow only proved request-item, assignment, physical receipt, handover item/receipt, inventory effective binding, media origin, actual reuse manifest/return, batch member/output/discovery and downstream operation links. Related subject existence is not general access. A case-specific investigation grant permits its allowlisted evidence, not the whole graph. Same-ID facets collapse to one physical subject; genuine derived/discovery media show their real origins with distinct labels, never invented first receipt/detachment. For recognized discovery keep the genuine older origin.

Default timeline order is recording time descending, then event ID, with cursor pagination (25). Show observed and recorded Nairobi instants distinctly; late records remain discoverable at the top. Render original facts and superseding review references together, plus a current-status panel recomputed under current scope. A corrected report never erases its old entry. Operation/physical events sharing one command are grouped with one physical fact per subject: first-receipt operation versus item event, handover operation versus accepted item event, return acknowledgment versus manifest member events, downstream acceptance versus canonical custody event. Staff may expand the authorized original references; Consumer sees owned safe milestones only.

Consumer batch association shows **Linked to batch; outcome pending / recorded outcome / current exception**, with only owned input codes, no batch kg, other members, staff details, private serial/contact/evidence or per-device recovery percentage. Genuine historical close plus later evidence shows both; never flatten to Recycled. An owned parent's derived-media association conveys lineage, not a new collection. Collector private history links require current assignment/route/custody scope; revocation removes details. Processor original source staff see their authorized lineage and safe destination outcome references; a destination recipient sees its shipment and accepted unit/slice, not the full mixed-owner source batch. Administrator aggregate reports do not bypass private case/evidence grants. All old links reauthorize live; a revoked link returns safe Not available rather than cached detail.

## 7. Required notice map and delivery behavior

Each N entry below specifies authoritative event, wording, recipient/link and owning delivery family. **Dedup key for every entry is `(authoritative operation event ID, recipient user ID, 'in_app')`**, using the existing outbox unique constraint; each logical update has exactly one family owner. Aggregate multiple owned members for the same recipient into that one notice. Unified inbox is a scoped union over five existing family tables plus one new milestone table, using typed family/notice keys and existing read state; never copy legacy notices into another table.

- **N01 Registration/self-report:** actual `item_registered` / `self_report_revised` from RegisterDevice. “Item registered” / “Your self-report was updated; this does not approve collection.” Owner only → owned item timeline. New milestone family; registration is not collection.
- **N02 Request/preference/review:** `request_submitted`, `request_items_cancelled`, `request_date_preference_changed`, `request_eligibility_revalidated`, `request_review_recorded`. “Request recorded / preference changed / review recorded; no appointment is booked.” Owner, and currently relevant assigned actor only where the existing request authorizes the affected work, → owned request/current assigned job. New milestone family; approval/Ready means eligible for next controls, not scheduled/received. Do not decrypt or display payload reason ciphertext.
- **N03 Assignment/plan:** existing `assignment_offered/accepted/declined/withdrawn/replaced/invalidated/completed/remainder_review` stay with assignment family and its existing relevant owner/Collector/coordinator recipients. “Accepted — not scheduled”; visit completion/remainder wording must not say every subject was collected. New `route_plan_approved` / `route_plan_withdrawn` notices use milestone family, scoped to named Collectors and owners of selected actual proposed-plan assignments, not excluded jobs or other routes → Collector's current approved route / owner's request. “Simulated pickup plan approved/withdrawn; no booked appointment or physical receipt.” No notice for merely comparing routes. A computed stale-plan banner is not a fabricated scheduling event; use an existing causal assignment/exception notice where one exists, never emit a physical transition from polling.
- **N04 First physical visit/receipt:** `physical_visit_recorded` plus referenced `receipt_outcomes`/actual `first_receipts` → existing receipt family, owner → receipt result/owned timeline. “Visit recorded; [own accepted/absent/refused/held] items shown.” A first receipt milestone requires its actual `first_receipt` event. Do not send a second new-family alert for each child event, or call an absent/held/untouched subject collected.
- **N05 Custody handover:** `handover_initiated/acknowledged/withdrawn/resolved` with actual `handover_receipts` where accepted → existing handover family, named current sender/recipient and affected owner subsets → currently authorized handover/owned timeline. Initiated is “Handover proposed”; acknowledged shows only actually accepted members and exceptions. `handover_accepted` enriches lineage but creates no second notice or new collection. Closing without transfer does not say delivered.
- **N06 Inspection/human decision:** `inspection_recorded` and `pathway_decided`, tied to actual inspection step/decision → existing assessment family, owner and scoped accountable staff → stage/owned timeline. “Inspection recorded; separate decision required” versus “Human pathway decision recorded; work not yet performed.” Keep original recommendation distinct from human decision and later supersession.
- **N07 Treatment assurance/applicability:** `sanitization_attempt` only on failed/incomplete/otherwise action-requiring result; `sanitization_validation` accepted/rejected and `sanitization_revalidation` accepted/rejected → new milestone family, currently controlling responsible Processor and safe affected owner → scoped sanitization/owned timeline. “Treatment assurance record accepted” or “Applicability review recorded / review required”; no claim hardware was executed, a new treatment occurred on revalidation, or release is authorized. Verification alone, authorization, evidence upload and discovery are not successful treatment. Current newer failure/incident badges remain visible even on an older success notice.
- **N08 Refurbishment/reuse:** `refurbishment_work` completed/failed/incomplete and `refurbishment_test` passed/failed/incomplete → new milestone family, responsible scoped Processor/owner → scoped work/owned timeline. “Work/test result recorded; release remains separate.” `refurbishment_authorize/withdraw/exception/acknowledge` → same family, named existing owner and authorized issuer → exact return authorization/owned timeline. “Ready for owner acknowledgment” is not released; only actual acknowledgment says “Owner acknowledged reuse return.” `reuse_returned` member events support custody/lineage, not duplicate alerts. Work-applicability is review, not repeat work.
- **N09 Dismantling/production:** `batch_commit` with `dismantled_in_batch` physical references; `batch_output`, `batch_measurement`, `batch_accounted`, `batch_discrepancy` → milestone family, source responsible staff and affected owners via safe own associations → source batch / owned timeline. “Dismantling / output accounting recorded; downstream outcome pending.” Routine draft edits do not notify owners. Multiple member events do not create one alert per join; one batch operation/recipient. No claim recycled mass allocated to an owner.
- **N10 Downstream:** actual `downstream_dispatch/accept/refuse/shortage/dispute/source_loss/downstream_loss/measurement_dispute/complete/close` → milestone family, current named destination actor/source responsible staff as relevant and safe original-owner associations → current shipment/source accounting/owned timeline. Draft alone is staff preparation, not dispatch; notify the named recipient when actionable reservation/dispatch work is recorded. Accepted, completed and closed are separate. “Recorded recovery/disposal/controlled storage/loss” uses exact supported kind and current evidence status. Aggregate acceptance is quantity accountability, not whole-lot custody. Use `downstream_accept` as the notice event; `downstream_accepted` canonical physical event adds no second alert. A close notice retains its original time with current later-exception badge.
- **N11 Recipient responsibility:** `restriction_approve` for same-destination succession remains restriction-family proposal notice; do not duplicate it in milestone family. Actual `downstream_recipient_accepted/cancelled` → milestone family, accepted/proposed successor, source coordinator and prior actor only if still currently authorized → current shipment/case. “Responsibility accepted/cancelled; physical acknowledgment remains separate.” No old-generation action/evidence link or inferred receipt.
- **N12 Corrections/impacts:** `restriction_open/assign/revoke/clarify/note/proposal/continue/close/approve/fulfill` → existing restriction family. Retain its current actor/coordinator/investigator/invited-party recipients; extend only safe affected owner membership where a batch case has no direct item owner. Staff → explicitly authorized case; Consumer → own timeline/own affected-item list, not private case. “Review/continuity/fulfillment recorded; current obligations shown.” Close without change retains blocker. A new attempt/incident/measurement event that contradicts completed work uses its actual causal N07/N09/N10 notice plus live exact obligation badge; do not invent a second generic resolved/exception event or claim all dependent obligations cleared.

Owner fan-out traverses immutable original input/owner ancestry and effective valid associations, not ownership guesses or raw arbitrary family expansion. Source staff cannot become recipient through that fan-out. The current named receiver, granted scope and independent case evidence remain separate. Existing family notification IDs/read timestamps are preserved. No “email sent” or hardware/certification claims occur.

Delivery defaults: scheduled in-app polling every minute, **100 eligible rows per batch**, row locking/skip-locked, one row's delivery plus outbox success state atomic, idempotent retries. Persist failed attempt count after rolling back the failed delivery transaction, with safe fixed error code and next retry; no raw exception, reason, contact or evidence payload in logs. Up to **five attempts**, failure delays **1/5/15/60 minutes**, then Failed for authorized operator review. Transient failures retry; missing current authority is Suppressed/unavailable, not endlessly retried or automatically revived after scope restoration. Manual retry is scoped, audited, rechecks source/recipient authority and reuses the same dedup key. Failure visibility is a safe own inbox banner and Administrator delivery queue (counts/reference/error code, no private payload). Committed domain facts survive delivery failure; an outbox insertion belongs to its domain command transaction.

At implementation activation, freeze an explicit **new-family cutover event watermark** and allowlisted event types during a controlled application cutover. Future new-family outbox inserts carry an immutable delivery-family/version tag; the new worker requires that tag and the matching real event, not a timestamp or pending state alone. Old untagged rows for newly supported families remain untouched, including a pre-cutover transaction that commits later. New producers/worker cover subsequent versioned committed events only by default. Migration must not synthesize notices, run workers or drain old registration/request/other unrelated pending rows. Existing five families retain their typed behavior/history; any bounded operator-selected legacy replay needs separate explicit preview/authorization and dedup tests, not a wildcard worker. No external channel/provider added. “Delivered” means stored in this recipient's in-app inbox, not read, externally emailed or physically acted upon.

## 8. Fixed CSV contracts and private lifecycle

Use the **same normalized filter set, selected membership, authorization, metric definitions and report revision** as the displayed snapshot. Export POST requires its current signed context token; if effective facts, membership, redaction or scope changed, show **Report changed — refresh and generate again**, not a silently different file. Each file is an immutable generated snapshot with UTC generation instant, Nairobi generation display, definition/report revision and correction references. At download, a changed dependency invalidates the file and requires regeneration; this avoids serving stale effective values while claiming they match a current dashboard. No historical as-of engine is introduced.

Every CSV uses a normal fixed header, one row grain and consistent named metadata columns (not mixed metadata/preamble rows): `export_reference`, `report_kind`, `report_mode`, `definition_version`, `report_revision`, `generated_at_utc`, `generated_at_nairobi`, `timezone`, `cohort_basis`, `from_local`, `to_local`, authorized `facility_filter`, `facility_basis`, `category_filter`, and row-specific original/effective/correction references. Facility basis names first receiving place, first processing facility, batch source or incoming destination; those are not interchangeable filters. Repeat fixed metadata where needed; an empty result has header plus a typed summary row with `row_kind=summary`, zero counts and blank undefined rates. Summary/detail rows are explicitly distinguished and never summed together by an importer. No raw private dependency fingerprint or secret key in CSV/URL.

- **E01 Collections:** R01/R04 summary by original intake class/category/subtype and actual first receiving place; counts, known estimated kg, estimate-known/eligible counts, unclassifiable count. No names, owner IDs, serial/IMEI, contacts, addresses, precise locations or evidence. Consumer has no operational CSV in C17; own-data packages belong to C18.
- **E02 Facility cohort:** R02/R03 by first processing facility/category/subtype: cohort count, current qualified/historical acknowledged counts, numerator/denominator/rate, current outcome/incomplete/exception counts. Include generated current basis and safe opaque correction references; no other-facility evidence/actors. Total is computed from the eligible subject set, never an average of row rates.
- **E03 Batch accounting:** authorized source batch/output detail with `row_kind`, batch/output public references, commit/close observed and recording times, original/effective input/output measurements, P/D/Ls/R/A/V, accepted/recovered/disposed/storage/transit-loss/accepted-loss/pending/disputed kg, measured/eligible counts, variance/tolerance/status, historical/current closure labels and opaque review references. Separate batch summaries from output rows; input kg appears only on its batch summary so it cannot be double-summed. Authorized incoming shipment export is an explicit **incoming slice** mode with shipment/output references and its dispatch/receipt/outcome amounts only; omit source batch totals/membership, contacts and evidence. Incoming and source modes never combine into a facility recovery total. Unknown fields blank with explicit state/coverage.
- **E04 Collector manifest:** only a personally named current approved, unfinished **proposed** route and current accepted assignments/unconsumed stops passing existing Eligibility/Execution checks. One row per stop in approved order: route/approval/assignment/request public references, stop sequence, safe necessary outstanding item-code/category/subtype list and item count, frozen per-item/stop estimated kg clearly labelled, preferred local date marked **not booked**, authorized pickup contact/address/coordinates already available for that accepted work, and destination display name. Do not include unrelated/consumed/withdrawn work, other Collectors, full run snapshots, reasons, owners' other assets, serials/evidence or comparison/baseline tours. A date/category filter must not silently omit part of an approved stop; manifest uses that route's whole current authorized outstanding work, with filter metadata naming the exact route/approval instead of pretending it is a date-cohort report. Current on-screen manifest and CSV share that set. Administrator/Processor cannot impersonate a Collector through this export; oversight uses aggregate reports/existing scoped routing views.

CSV encoding: UTF-8, explicit comma delimiter, RFC-style quoting/doubled quotes and CRLF records through a standard writer. Protect **each untrusted text cell**, including contact, codes, material/category labels and metadata: remove/reject embedded NUL/disallowed controls; neutralize leading `=`, `+`, `-`, `@`, tab/CR/LF and whitespace-prefixed formula triggers with a leading apostrophe, then quote normally. Do not rely on quoting alone. Known numeric fields come only from canonical numeric formatters (a genuine signed variance stays a number); text is never retyped as numeric by user input. Test Excel/LibreOffice-style formula strings without launching external links. No executable attachments, spreadsheet macros or extra PDF/signature package.

Proposed lifecycle: private local non-served export disk, randomized opaque ID/storage key, authenticated requester-only retrieval (no bearer/public signed URL), download filename without names/contact. General E01–E03 retrieval expires **24 hours after generation**; contact-bearing E04 **30 minutes**. Any scope/session/policy generation change, source correction/receipt/route drift or redaction invalidates earlier than expiry; restoring access does not revive the old file. Check expiry/current actor and all referenced scopes at request, generation, immediately before publishing and immediately before sending download bytes. Recheck before first byte under the existing mutation/scope gate; do not stream unchecked rows or leak a partially authorized file. Downloaded copies cannot be recalled; say so in plain manifest handling guidance.

Bound defaults: one generation in progress per user, five generation requests/hour, **10,000 rows / 10 MiB / 15 seconds** maximum per general export; E04 maximum existing **50 stops / 2 MiB**. Bound row selection before decrypting contact; no background provider/dependency needed. If limits/timeouts hit, fail completely with Narrow filters, no partial ready file; limits do not raise existing NF03/NF04 targets. Use stable ordered chunking within one consistent snapshot and bounded file buffering. Ready state/file reference only after successful authorization/commit; compensate only newly created unreferenced temporary files on failure/root COMMIT rejection. Existing files/keys are never removed for a failed new export.

Record requested/generated/failed/download-allowed/download-denied/expired/invalidated outcomes with actor, time, safe reason code, scope/report revision and opaque export reference. No CSV content, contact, ciphertext, private path, token or evidence in access logs. Expired bytes are inaccessible immediately and cleaned by a bounded owned-artifact job; this is a **proposed temporary artifact lifetime**, not approval of a general privacy-retention policy or C18 deletion request. Keep only minimal audit metadata pending C18's explicit retention/redaction decision; this does not override D2's existing synthetic/evaluator-data obligations or authorize perpetual retention. Inventory CSV bytes, temporary files, metadata/filter/source-reference manifests, audits, delivery error metadata and any later caches for C18; do not silently exempt them from redaction/backup review or invent an audit deletion schedule now.

## 9. Africa/Nairobi display and compatible local entry

Keep database instants and application timezone UTC. One shared display/parse helper and Blade time/field components render **Africa/Nairobi (EAT, UTC+03:00)**, with explicit observed versus recorded labels and a UTC machine-readable instant. Audit core role/device/request/assignment/route/receipt/handover/assessment/inventory/sanitization/reuse/batch/downstream/restriction/notice/export screens; do not fix only the new dashboard. Labels, filenames and CSV time columns are consistent; file expiry also has explicit timezone.

New browser forms submit a versioned Nairobi-local minute field, e.g. `observed_at_local` plus fixed `time_basis=africa_nairobi_v1`. Strict server parsing validates real calendar date and exact format/round-trip, rejects offset/timezone substitution, converts once to UTC, then applies unchanged existing source/case/now/retrospective limits and reason requirements. Ignore the browser computer timezone; minimal JavaScript is optional, server conversion authoritative. Do not silently supply now for missing/invalid input. New local fields and legacy UTC `observed_at` cannot be mixed in one request. Preserve safe allowed values/errors under the existing private-field/file reselection contract.

Legacy UTC forms/clients without the new marker retain the exact former UTC interpretation and payload normalization. Remove transport-only local fields after conversion; existing domain validation, context snapshots and command hashes still receive canonical UTC values. Historical identical retries must return their original result before freshness rejection without creating events/notices; changed instants conflict. No historical timestamp, successful command, encrypted snapshot or key is rewritten. Minute precision remains the existing contract, not implicit rounding of a new seconds field.

Date-only `preferred_date` remains a Nairobi calendar **preference**, never an appointment/UTC midnight instant; compare local Today for current validation, preserve original stored dates and historical retries. Report From/To boundaries convert local midnights once to a half-open UTC interval; no `DATE(utc_column)` shortcut. F-T assertions: Nairobi `2026-10-23 00:00` = `2026-10-22 21:00Z`; `23:59` = `20:59Z` same UTC date; next local midnight is exclusive; late recording does not move a physical first receipt into the recording-date cohort. Include leap day, impossible dates, future observations, source lower bound, two different browser timezones, both old/new forms and same/changed command retries. Native guards continue comparing actual UTC instants.
