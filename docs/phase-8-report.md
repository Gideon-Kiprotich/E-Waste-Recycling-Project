## Authorization, evidence and privacy

**Place staff access** extends the existing point-scope page and route/payload contracts to collection points or facilities. It links/revokes existing Processor accounts only, retaining one explicit place under an approved processor/both operator. Actual changes remain audited, increment account/session/membership versions and revoke sessions; identical active links remain audited no-ops. Existing scopes are not widened or backfilled. Private local staff provisioning remains separate.

Every handover names an eligible receiving Processor and freezes its membership version and destination/operator versions. Exact category/subtype capabilities are required for all selected items, including standalone drives/fans. Account, membership, organizations, places and capability rows are locked/rechecked under the existing transaction gate. Current source party must match every selected received subject. Header/item reads are filtered by current role/scope/ownership in the database and checked again before presentation or mutation. Consumer ownership never changes. Administrator oversight permits pending withdrawal and discrepancy review, never recipient acknowledgment. Replacing/revoking scope grants no replacement recipient access to an old handover; use withdrawal or discrepancy review and fresh initiation instead.

Manifest reasons, per-item physical comparisons/review reasons and operator reference details are encrypted. Each operation requires one private JPEG/PNG/non-active PDF up to 5 MiB, or an accountable issuer/record number with explicit staff assertion. Existing image re-encoding/metadata removal and private storage are reused; no external reference is fetched and no signature/independent verification is fabricated. Bytes are included in keyed retry comparison. Rollback removes only newly uploaded unreferenced evidence.

Scoped participants and Administrators see authorized manifest/evidence; old links recheck live scope. Consumers see only owned items and their affected operations/milestones, without other owners' items, private observations, references, pickup contacts/addresses, identifiers or evidence. Handover evidence uses its operation FK, separate from owner registration-photo links. Notice text remains minimal after scope loss; following a notice link reauthorizes access. Private fields/uploads are not flashed after validation. Existing feedback summaries, linked errors, explicit labels, persistent messages, camera/manual lookup and responsive CSS are reused. HTML assertions do not establish visual or assistive-technology acceptance.

## States and custody effects

- **Initiated:** explicit sender manifest acknowledgment/evidence creates pending items. Confirmed custody remains with the sender. One partial unique index reserves each subject across active pending/disputed transfers. No automatic expiry exists.
- **Pending → accepted:** only the named currently eligible Processor can attest matching physical label/category/subtype/model and actual receipt. An immutable acknowledgment/outcome and subject event atomically advance custody to the destination **place**, retaining the real actor separately. Scanning selects only; it never acknowledges.
- **Pending → disputed:** explicit missing/damaged/mismatch/refused outcomes retain last confirmed sender custody and an active blocking claim. Recorded accountability is distinguished from disputed physical whereabouts. Omitted/Leave pending items remain unchanged; mixed outcomes are supported.
- **Pending → withdrawn:** current original sender or Administrator supplies reason/evidence. Only selected pending claims release; accepted/disputed history cannot be withdrawn.
- **Disputed → disputed:** Administrator **Continue investigation — retain claim** appends evidence/reason without resolving or releasing it.
- **Disputed → resolved:** Administrator **Close dispute — no transfer/return recorded** requires explicit evidence-backed closure attestation. It releases that transfer claim while preserving the original dispute, outcomes and last confirmed custody. It is not a statement that physical return occurred. A replacement requires fresh initiation and recipient acknowledgment; no prior acknowledgment is rewritten.

Header state derives from item states: all accepted → accepted; any unresolved dispute → disputed; all pending → pending; pending mixed with terminal outcomes → partial; otherwise closed. Every operation advances one header version and appends history. Same actor/action/key/payload retries reauthorize then return the original safe result before stale-state gates; changed payloads conflict. Named uniqueness failures become safe conflicts; unrelated database errors propagate. Timestamps retain explicitly labelled UTC entry, separate server recording time and Africa/Nairobi history display; the separately deferred Nairobi UTC-entry usability issue is not represented as fixed.

Acceptance records a collection-point/facility receipt milestone, with destination kind retained in the immutable accepted event so later directory reclassification cannot rewrite that milestone. It does not establish inspection, processing, sanitization, actual route arrival or legal certification. It does not create a second first receipt, collection count, owner, storage identity or mass entry, and does not reopen completed requests/reservations/assignments.

## Database integrity, migration and preservation

Forward migrations `2026_10_15_000005_create_custody_handovers`, `2026_10_15_000006_preserve_handover_execution` and `2026_10_15_000007_retain_current_custody` add six ledgers/projections: handovers, items, operations, outcomes, receipts and notifications. Historical migrations are unchanged. Operations/outcomes/receipts are append-only; header/item identity and allowed projection transitions are guarded. Deferred reciprocal checks require complete manifests, operation/outcome history, acceptance receipts, derived states and current custody at the enforcement boundary.

The original first-receipt proof stays immutable. Its projection guard now validates current custody against the continuous accepted handover chain: source party/event and custody/subject versions must match the prior confirmed event, increments must be consecutive, and the latest accepted event must match current custody/version. Direct skipped/fabricated custody, orphan accepted projections and historical rewrites are rejected. A standalone HDD/SSD facet retains the drive's one subject/custody identity.

Focused tests exposed an additional preservation issue: the existing subject-version dependency trigger invalidated a still-approved route after a legitimate later handover. There is no session flag, disabled protection or general invalidation bypass. A subsequent rollback-only regression demonstrated that direct deletion of a current-custody row was not covered by update-only receipt guards. The third migration rejects deletion or reassignment of the custody row’s subject key, preserving ordinary acknowledged updates; it refuses an existing missing-custody condition rather than inferring history. ## Exact-label walkthroughs

1. **Collector → facility:** finish **Operators and places** review/capabilities, provision an existing Processor privately if needed, then **Place staff access → Link or reactivate at selected place → Save place scope**. After actual pickup receipt, Collector opens **Custody handovers → Prepare handover to [named Processor · facility]**, selects held items, manifest acknowledgment, time and evidence/reference, then **Initiate pending handover**. The named Processor signs in and opens **Custody handovers → Open handover → Record recipient outcomes**, optionally **Select label / Scan with camera**, compares each physical item, selects **Accept — actually received and matching**, attests and supplies evidence/time, then **Record recipient outcomes**. Only accepted rows gain facility custody. Consumer **My devices → device detail → View your handover milestone** shows owned safe outcomes.
2. **Collection point → facility:** after actual point drop-off or an accepted Collector-to-point handover, its explicitly scoped Processor opens **Custody handovers** and follows the same initiation steps to a named facility Processor. Completed request/assignment state does not require new collection allocation. Destination Processor acknowledges individually. Facility staff cannot redistribute onward in this increment.
3. **Partial/disputed:** named receiver sets actual matching items to Accept, explicit missing/damaged/mismatch/refused outcomes for discrepancies and **Leave pending** for omissions. Sender/Administrator uses **Withdraw pending items** only for pending rows. Administrator **Custody handovers → Open handover → Review discrepancies** selects **Continue investigation — retain claim**, or **Close dispute — no transfer/return recorded** with supporting evidence/reason and closure attestation, then **Record discrepancy review**. Prior outcomes remain visible. A justified replacement starts a new pending handover and needs fresh recipient acknowledgment; closure itself never changes custody or declares return.
