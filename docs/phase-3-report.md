## Scope and requirement coverage

- D2 FR04/FR07–FR09, BR02/BR03/BR05/BR11/BR15–BR17/BR20; D3 US04–US05, UC04–UC05, S04, §§3.3/4.5/5.5/6.1 and AT03/AT11: owned multi-item pickup/drop-off requests, directory compatibility, geography, private details, reservation integrity, preference/cancellation history and accessible feedback.
- CR-PARTS-01: independently registered HDDs, SSDs and small ICT fans remain single physical subjects. Storage facets do not add selectable units or duplicate mass. Points must explicitly accept each subtype; laptop acceptance never grants loose-part compatibility. CR-ID-01 encryption, global uniqueness, label/lookup and retry behavior are unchanged.
- Devices → Collection method → Location → Review is a server-rendered four-step flow. Each relevant step validates input; final submission revalidates ownership, account/session, category/state, reservation, observations, date, point and area under transaction locks. A request has 1–25 individually registered items; this form limit is an engineering choice, not bulk intake.
- My requests and actual history are paginated (12 requests/10 events). Only the current Consumer owner can access private request detail or change outstanding items. Other Consumers receive 404 for owned-detail paths; Collector/Processor/Administrator access is not granted before the later scoped workflows exist. The public point list contains minimal directory/capability data and no user request information.

## Decisions and behavior

Submission returns an opaque `EWR-` reference and **Awaiting review** (`SUBMITTED`). A preferred date is not an appointment. Item processing state, identity, storage metadata and confirmed custody do not change on submission, date preference changes or cancellation. There are no scheduling/receipt endpoints or fabricated outcomes.

`REQUEST-ELIGIBILITY-1.0` distinguishes:

- **Blocking:** non-owned/unsupported/non-registered item, active reservation, invalid required input/date/location, inactive/unapproved/incompatible point or area; a fan now known to be outside scope (`fan_scope=NO` or `fan_electronics=ADDITIONAL`) cannot enter a new request or change its date preference.
- **Permitted into review:** safety YES or UNKNOWN; fan scope UNKNOWN or electronics UNKNOWN. Controlled reason codes explicitly require human review and withhold ordinary scheduling. A previously submitted fan later found outside scope retains its reservation/history and receives an explicit scheduling-blocked reason; cancellation remains available before receipt.
- Unknown past function/physical condition alone is not converted into a declared hazard. Data-bearing status is separate: HDD/SSD remain YES, with later sanitization/release gates intact. An empty list of additional review reasons does **not** mean operator approval: every request remains awaiting review in this increment.

Each reservation retains its immutable initial observation ID/revision, subject version, initial review reasons and rule version. It also tracks the current observation/version/reasons. A successful self-report revision refreshes any outstanding reservation inside the existing device transaction, advances request version and appends a request revalidation event/outbox reference using the observation command. Retried revisions do not append twice. Known and uncertain changes cannot silently clear normal scheduling. Later operational review must revalidate current observations, point status/capabilities and geography before any scheduling workflow.

The initial request header date remains the submitted preference. Current preferences are per item, so changing a selected subset does not silently change the others. Cancellation releases only selected outstanding reservations and retains their final rows and encrypted reasons. Fully cancelled requests become CANCELLED. The header projection also understands collected/mixed outcomes for future compatibility; receipt/received states are exercised only as isolated test fixtures. Cancelled/collected outcomes cannot be reopened. Consumers cannot change received/ineligible items.

Mutations lock the current actor/membership, then subjects/items in sorted UUID order, then the existing request/configuration as needed. Expected request versions reject stale changes. Commands use the existing actor/action/key uniqueness, keyed canonical payload digest and safe original-result replay; changed payloads return 409. Successful retries resolve before current reservation/date eligibility, including when an old preferred date has passed. The active-item partial unique index is the final reservation race protection. Request/private row, reservations, command, immutable event and pending outbox rows commit together; unrelated database failures propagate, and only the named reservation uniqueness conflict receives the safe reservation field error.

Wizard drafts are encrypted in the server session, bound to the owner, and versioned. A stale tab cannot submit a newer unreviewed draft. Failed step edits invalidate completion of subsequent steps. At the initial collection-request commit, private addresses/contact/coordinates never entered URLs, browser persistent storage or audit payloads and no geolocation API was introduced. The separately authorized map enhancement below adds explicit opt-in geolocation. Typed safe fields are retained; unsupported/null/array protected fields cannot become old input. Error summaries use existing focus behavior and associated errors, with persistent success/information/error feedback. Messages and user text are escaped by Blade. No notification library or frontend dependency was added in that initial commit; the follow-up below adds only Leaflet.

## Directory and geography assumptions

The two forward migrations create minimal organizations, collection-point places, exact `place_categories(place_id, category_id, subtype)` capabilities and versioned service areas. Empty subtype means an explicit whole-device capability, **not a wildcard**. Parts require hdd/ssd/ict_cooling_fan; peripherals require router/keyboard. Database guards reject mismatched capability vocabulary. Organization approval requires a recorded review time/reason; this schema foundation is not an implemented operator-review workflow.

Migrations seed **no** organizations, points or areas. The explicit local command `php artisan app:setup-collection-demo` creates only:

- One labelled synthetic study operator, with simulated approval and an explicit non-certification reason.
- An active all-ICT point with explicit HDD/SSD/fan capabilities; an active whole-device/peripheral-only point; and an inactive all-ICT point. These are fictional configuration cases, not real facilities.
- `SYNTHETIC-STUDY-1.0`, a hand-defined rectangle: latitude −1.350000 to −1.200000, longitude 36.750000 to 36.900000. GeoJSON uses longitude/latitude order. Point-in-polygon includes edges/vertices with a documented 0.000001-degree tolerance (roughly 0.11 m here, not road distance). **This is not the official Nairobi County boundary.** Geometry/provenance/version identity is immutable; revisions need a new area row/version. Active status may change.

Setup requires APP_ENV=local, a verified dedicated localhost project PostgreSQL connection/owner and non-elevated ewaste_app. Repeats retain all existing rows and deliberate active/capability changes; they do not reactivate points or restore removed capabilities. Synthetic code collisions with non-synthetic data fail transactionally. No staff membership, contacts, licences, capacity, transport prices or real operational acceptance is invented. Real facilities/areas must obtain actual capability and geography evidence before real service is offered.

The consumer routes consolidate cancellation/date changes into POST `/requests/{id}/change` with an explicit operation, and final submission uses POST `/requests/create/4` against the encrypted wizard draft. These are bounded implementations of UC04/UC05, rather than additional downstream API workflows.

## Tooling vulnerability assessment and remediation — 6 October 2026

This is the separately authorized assessment of the two findings reported after `Improve pickup location` (`f6bf49bedddf7d20a3ff373ed35ec8d2a21c2425`). The starting working tree was clean on `phase-3-collection-requests`. This increment changes dependency resolution and targeted tooling tests, not collection features, PHP dependencies, database state or the phase's acceptance status.

### Findings and primary evidence

`npm audit --json` reproduced **two critical package entries with one underlying advisory**, not two independent flaws:

- **shell-quote 1.9.0**, transitive dev dependency: root → concurrently 10.0.5 → shell-quote 1.9.0. Advisory **GHSA-pqg4-j6r4-53mv / CVE-2026-102422**; affected releases **>=1.8.4 and <1.11.0**; first patched release **1.11.0**, verified in the [maintainer's advisory](https://github.com/ljharb/shell-quote/security/advisories/GHSA-pqg4-j6r4-53mv) and [fix commit](https://github.com/ljharb/shell-quote/commit/6002b2ed90c6b83095eb272b6b0adaf3a172b0bc). Its quoting function permits shell comment termination through a line break in a later string token. If that output is executed by a POSIX shell, attacker-controlled syntax can run. The patch rejects LF, CR, U+2028 and U+2029 in strings after a structured comment token. An in-memory pre-fix probe accepted all four sequences; it executed **no shell**.
- **concurrently 10.0.5**, direct dev dependency (`^10.0.3`), at root → concurrently. The audit entry's `via` is shell-quote, propagating **the same GHSA/CVE** through its exact 1.9.0 dependency pin. There is no second concurrently advisory or distinct first patched concurrently release for this finding. Registry metadata and the [upstream release history](https://github.com/open-cli-tools/concurrently/releases) still identify 10.0.5 as latest. We retain that version and fix its resolved child, rather than claiming the upstream package was released with a new dependency pin.

The [maintainer advisory](https://github.com/ljharb/shell-quote/security/advisories/GHSA-pqg4-j6r4-53mv) rates the vulnerability **High (CVSS 3.1, 8.1)**. Separately, the earlier npm audit classified its two package entries **Critical**, and the [GitHub reviewed database record](https://github.com/advisories/GHSA-pqg4-j6r4-53mv) labels it Critical with CVSS 4.0, 9.2. These source-specific classifications are preserved; the maintainer's rating is not described as Critical. The differing labels do not remove the need for a patched installation.

### Actual project exposure

Both entries concern **local development runner tooling**, installed alongside build tools. They do **not** affect production browser assets, and the affected package is not called by `npm run build`:

- `composer.json`'s development script invokes concurrently with fixed `composer run serve` and `npm run dev` commands, names and `--kill-others`. It supplies no passthrough flag/placeholders, parsed comment tokens or consumer-controlled values. These scripts intentionally launch local shell commands; they are not HTTP command-execution endpoints.
- Inspection of installed `concurrently/dist/bin/index.js` and `lib/command-parser/expand-arguments.js` shows that its optional passthrough path converts CLI arguments to strings and calls `quote()` on strings/string arrays. It does not combine `shell-quote.parse()` comment objects with subsequent untrusted strings. The project's ordinary development invocation does not enter that optional path at all. The advisory's required structured-comment-plus-later-line-terminator pattern is therefore **not reachable through the inspected current application/scripts**. This is a code-based reachability assessment, not a blanket exemption for dev dependencies.
- `npm run build` directly runs Vite; `vite.config.js` imports the Laravel Vite plugin, not concurrently. A read-only Vite module-provenance build recorded application modules, Leaflet/CSS and Vite's preload helper, with neither affected package in the browser module graph. All **nine** production assets/manifest files are byte-for-byte identical before/after remediation. `npm ls`/`npm explain` show no other project dependency path to shell-quote. No consumer contact, address, coordinates or uploaded file names are supplied to this runner.

If another tool or a future integration used the vulnerable structured quoting pattern with attacker-controlled input, injected commands would run with that developer/CI process's permissions and could affect its accessible checkout, configuration and files. Current script reachability limits direct exposure; it does not make retaining vulnerable code a safe long-term disposition. The dependency is remediated below rather than suppressed.

### Targeted compatible remediation

Added a root [npm override](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#overrides) scoped to concurrently's child:

```json
"overrides": {
    "concurrently": {
        "shell-quote": "1.11.0"
    }
}
```

`npm install` changed **one package**, shell-quote 1.9.0 → **1.11.0**; the lockfile diff changes only its version, archive URL and integrity. Concurrently remains **10.0.5**; Vite, Leaflet and all other package versions are unchanged. Both child versions use the same compatible Node engine minimum; concurrently retains Node >=22. The first patched minor release was chosen rather than an unrelated latest-version sweep. Its [maintainer changelog](https://raw.githubusercontent.com/ljharb/shell-quote/v1.11.0/CHANGELOG.md) and actual compatibility tests support this substitution for the string-quoting calls used by the runner. Rejection of dangerous structured inputs is the intentional security behavior change.

npm's automatic proposed resolution was a semver-major downgrade to concurrently **9.2.1**, outside the declared range. That is not necessary with the tested scoped override, and was not applied. No `npm audit fix --force`, downgrade, ignored advisory, severity threshold, new direct shell-quote dependency or broad upgrade was used. `npm test` now retains the five pickup tests and additionally runs five dependency-security/runner tests, resolving shell-quote through concurrently's actual installed dependency rather than an unrelated copy.
