## 3. Own scope, identity and request lifecycle

Recommend active authenticated users of the four existing roles may request their own personal data only; the extra staff self-service permission is proposed, not existing UC18 authority. Fresh password confirmation ≤10 minutes, current session_version, CSRF and current account/membership are required for submission, approving changed scope, package generation/download and final account closure. Never put a user_id supplied by the client in charge of scope. Suspended/redacted users gain no normal login exception: an assisted request stays identity_pending until existing recovery or an explicitly documented, approved study verification procedure establishes the original account. An Administrator must not impersonate the requester, invent proof or demand national IDs. No configured verified channel means pending, not an invented identity success.

Resolve targets server-side from the requester and their fields/relationships. Owning an item is not owning all its staff evidence, other batch members, a shared directory record or the whole restriction graph. Processor/Collector facility powers do not enlarge an own-data package. Current custodianship and historical ownership are different. Case grants disclose only necessary classified targets, not unrestricted lineage. A reviewer may inspect field classifications/references without decrypting unrelated evidence.

Request types: access, personal_correction, redact_delete; each can select account/contact, requests/locations, identifiers/photos, authored private material, notices/exports, or all own personal surfaces. A request records requested scope and later approved/retained/refused portions separately. Free text/new values are encrypted, ≤2,000 characters; no values or uploaded content in safe events, notifications or audit reasons. Optional proof uses existing private upload validation and explicit ownership; unnecessary identity documents are not collected.

States: submitted → identity_pending or scope_review → needs_information / dependency_review → approved or partially_approved / declined_with_reason → prepared → executing → partially_fulfilled or fulfilled. Withdrawal is possible before prepare; after an irreversible step it can stop remaining authorized steps but cannot undo erasure or revive old authority. Decline only with a specific scope/verification/unsupported-action reason. A retention question creates a dated residual obligation, not blanket rejection because audit history exists.

Consumer flow stays within S16: choose access/correction/deletion and own sections, read the effect and confirm identity, then see a request reference with requested scope, current status, plain reason, next action and due date. A package-ready state shows its expiry; partial erasure lists actual completed fields separately from retained/shared/backup portions. Account closure explains the final sign-in/receipt window before confirmation. Use existing labelled fields, feedback/error summary, keyboard focus and private-field reselection conventions; do not display SQL, plan capabilities or hashes. Publish a truthful new notice version only when the behavior is implemented; preserve prior notice/acknowledgment history and do not treat acknowledgment as permission for new uses.

Submission/review/execution use distinct actor/action/idempotency keys and expected versions. Two requests targeting the same resource serialize under the existing gate and native target claims. A retry returns the same safe reference only for the same still-available normalized payload; expired/redacted payloads get an unavailable tombstone, not accepted changed input or a repeated mutation. Partial status explicitly shows fields done, shared-evidence review, temporary expiry, retained identity comparison, backup_pending_until and next review.

Two distinct active Administrators are recommended for irreversible erasure/account closure: one verifies and proposes, another independently approves the exact plan and retention exceptions; neither is requester nor the technical evidence author for a shared-evidence disposition. One Admin may review/release an own-data package or non-destructive personal correction, never their own request. Existing private provisioning may establish the second reviewer; no general account-management screen is added. Missing independent authority leaves the case pending.

Filing a request changes no operational state. Prepare an account closure only after enumerating active requests/offers, custody, return authorization, downstream responsibility and obligations. Redact unrelated personal fields independently; keep only specifically justified contact/evidence while necessary work is reviewed. Closure need not fabricate completion or transfer custody: existing work can become ineligible/held and need existing review/actual counterpart action. No privacy actor may acknowledge on another person's behalf.

A proposed privacy-only account mode restricts authenticated access to own privacy status/receipt, current notice, recovery and logout during final execution; it grants no normal operational or evidence route. Enforce it at every normal reader/mutator and native actor gate, not just navigation. It is a narrow new privacy boundary requiring authorization, not an alternate role. Existing active work remains recorded, with current restrictions/ineligibility visible.

For explicitly requested account closure, show exactly which auth identifiers remain for the receipt window. After live steps are ready, allow up to seven days of privacy-only receipt access, or requester-confirmed Finish now; clamp to the study cutoff. Last authenticated confirmation can return a minimal decision receipt and end the session. Then users.status=redacted, membership inactive, version/session_version advanced and email/password_hash/remember/recovery/session data erased through the reviewed nullable-redacted constraint branch. No dummy email, password hash, surrogate actor or replacement owner is created. No login/tracking after full closure is promised; the requester must retain the receipt, and any assisted follow-up needs verified identity. Background failure remains visible to reviewers, not falsely delivered by email. This receipt/auth retention is disclosed as partial erasure until it actually ends.

## 6. Integrity, identity and the redaction mechanism

Recommend preserve original subject/public codes, actor UUIDs, custody versions, quantities, recorded times and command/event/relationship IDs while their finite project trace purpose applies. These remain pseudonymous and restricted, not anonymous or safe for publication. Render an unavailable personal label rather than creating a fictional actor or replacing every actor with one user. Existing physical states and historical closures remain original; current evidence qualification may become pending/exception. Reporting must distinguish them as C17 already does.

Identity choice needing explicit approval: remove clear serial/IMEI where justified, but retain existing identifier_hmac, kind and key version in a non-disclosing comparison-only store until the study retirement cutoff. Keep the same global unique binding, including derived/standalone/facet cases. Extend the triplet CHECK only for an approved privacy tombstone that permits ciphertext absence while comparison remains. Do not clear/rekey the HMAC, make duplicates valid, merge identities or claim full identifier erasure. Explain this retained portion and deadline in the decision. A demand for HMAC erasure while this identity namespace stays operational needs a separate permanent-identity policy decision, not a hidden privacy bypass.

Separate personal display/contact revisions from technical fact corrections. items.model, canonical identifiers and many snapshots are currently immutable: no privacy route changes them to a different asserted model/serial/owner or reconstructs provenance. Redacting unnecessary identifying text to an explicit unavailable state is different from correcting the technical fact. Unsupported identity correction stays referred/pending with reasons.

Proposed native execution protocol:

1. Lock the existing Review transaction gate (481204), requester/current role/session, request/plan version, sorted targets, shared references and any source/obligation epochs. Build a frozen typed plan with requested/approved/residual scope, current resource generations, allowed field codes, safe consequences and exact owned storage IDs. Per-request approval expires after 24 hours or on any source/authority/policy drift. PA08 standing expiry policy instead has a signed finite eligibility definition, current approving authority and at most 30-day review interval capped by the study deadline; it may create fresh exact due-target leases, never arbitrary edits or retention extensions. A service uses this recorded authority, not a fictional logged-in Admin or fabricated user session.
2. Commit prepared access denial, privacy epochs and durable work intents. Invalidate all affected C17 artifacts irreversibly, revoke sessions/recovery/URLs as approved, and prevent new snapshots/jobs from reading held targets. No original bytes are erased yet. Missing independent approval or an active unreviewed shared reference prevents the step. Expected privacy generations may advance only for this plan's own committed transitions; other drift requires renewed scope/approval. An expired approval never authorizes an additional destructive step, and its expiry cannot restore data already erased.
3. Persist the minimal replay intent durably to §9's independent register before destructive work. It contains opaque selectors/action/field codes, policy/plan/step versions, approval identity references and ordering, not old/new values, ciphertext, contact hashes, original file checksums or command payload hashes. Selector IDs still carry linkage risk and remain restricted.
4. A narrowly callable privacy_redact_step(plan, step, expected generation) may execute only the typed approved operation. Native guards verify the current approved row, real actor authority, exact target/field set, transaction-bound capability, lease and no drift. Do not trust a user-settable GUC, disable triggers, grant blanket UPDATE, change session_replication_role or accept arbitrary SQL/JSON paths. Preserve the existing non-superuser ewaste_app model; these guards do not claim protection against a compromised database owner with DDL powers.
5. Forward migrations add exact nullable/tombstone branches to the particular CHECK/immutability/reciprocal functions. Non-target columns must compare identically. Every permitted redaction must have a matching committed privacy step and every completed step must have its required redaction at root COMMIT. Missing-proof state must deny new assessment/work/release/dispatch/closure/recipient claims; privacy cannot satisfy technical gates. Never turn erased required evidence into successful, negative, unknown or N/A technical observations: it has an explicit privacy-unavailable status, separate from the retained original result. Do not rewrite event payload facts, fulfilled impacts, actor IDs or original mass.
6. For JSON/encrypted snapshots, classify every included path and dependency. Remove private components/copies only through the versioned adapter; if private and integrity data cannot safely be separated, quarantine the historical snapshot as unavailable and block its replay/current use. Do not write a newly valid hash over altered history. Existing signed core fields stay unchanged where non-personal; an erased signed input/digest means historical verification is explicitly unavailable, not that an altered signature still verifies.
7. Commands affected by erased identifying hash material retain actor/action/idempotency-key/result-reference tombstones and their completed historical operation. Approved payload_hash removal requires its own constraint branch. A tombstoned retry returns a fixed unavailable/410 result after current authentication; it neither accepts arbitrary changed input nor reruns the operation. Unaffected legacy retries remain byte-compatible. No digest of erased values is copied into the privacy ledger.
8. File work uses the existing private-disk safe path/ownership conventions. Mark access unavailable in DB before unlink; recheck every direct/stage/evidence link under the lease. A genuinely shared original is not unlinked merely because one party requested it. A valid reviewed derivative has a separate ID and explicit evidence implications; otherwise retain the justified original under a dated obligation and label partial. No automatic content rewriting that pretends to preserve proof.
9. DB/file/register cannot be one transaction. Record per-step prepared/register_durable/live_redacted/blob_deleted/verified states; root-COMMIT failure compensates only newly created derivatives, never restores erased PII. Unlink failure leaves all links denied and the step pending; crash after unlink is safely recognized as already absent. Leases are bounded; retry rechecks approval, scope, shared references and target generations. Never reuse stale authorization after restoration.
10. Completion verifies all selected live stores/copies, bytes, digest dispositions and residual deadlines plus register/backup state. Minimal audit is request/step code, action/outcome, policy version, real approval references and times. No erased field values, old filenames, raw requests, authentication secrets or erased-value hashes in that ledger. Replay selectors are a separately restricted part, not a publicly safe audit export.

The approved executor changes availability; existing native C14–C16 remain responsible for any consequent operational correction/continuity. If retained core evidence cannot support safe future progression after redaction, that progression stays held. Do not make erasure silently reverse a receipt or manufacture recovered stock.

## 7. Private own-data package

Separate from general reports: an access request's approved projection, not an export of the database or whole lineage graph. Include own account/notice data, submitted personal contact/request values still available, own item/self-report history, safe personal milestones, own privacy decisions and a readable section/coverage manifest. For staff, include their own personal account/action summaries without other owners' subject codes or confidential technical evidence. Include self-uploaded own device photos only where exclusive scope is proven and no other-person content/shared evidence is exposed; staff private evidence and unreviewed PDFs are excluded or handled by an approved derivative.

Exclude passwords/hashes, keys/configuration, reset/remember/session tokens, signed URLs, raw session payloads, other owners' names/contacts/coordinates, private staff findings, sensitive membership/delivery contexts and internal storage paths. Fields already erased stay unavailable; no recovery from backup for access. Explain each omission and retained portion. Provide human-readable HTML/text plus fixed-schema JSON/CSV; no database dump, executable HTML/script, arbitrary SQL filters or unsigned guessed file link.

Propose per-package 24-hour retrieval, 10 MiB/10,000 structured rows/25 selected files/15-second generation, private mode 0700 directory/0600 owned files, no overwrite and safe fixed filenames. Larger requests require an explicit partition manifest with complete approved coverage, not silent truncation/completed status. Apply C17 text/formula/control protection to CSV; sanitize human-readable markup. Bind to requester, authenticated session, request/plan/policy version, normalized scope, source/privacy revision and checksum. Reauthorize at generation, publication and immediately before first byte under the shared gate; session/scope/privacy/source changes permanently invalidate. Restore does not revive packages.

Reuse the fixed private lifecycle/compensation principles of [Exports](../app/Support/Reporting/Exports.php), [ReportSession](../app/Support/Reporting/ReportSession.php) and [PrivateCsvResponse](../app/Support/Reporting/PrivateCsvResponse.php). A proposed shared native generation lease/quota enforces one generation and five requests/hour across report and privacy packages, including stale attempts; do not bypass limits using a second endpoint. Expiry denies retrieval independently of cleanup; owned temporary files/abandoned 15-second leases are cleaned by bounded jobs. Package bytes and input values never enter logs/audits. Request completion records what was generated; download persistence is not proof the human received/read it.

## 8. Proposed finite retention profile

## 9. Backup and restored-backup handling

Backups are part of the erasure scope. Encrypted backups still contain data. Existing manifests prove preservation, not restoration or backup erasure. Inventory actual backup destinations, restore copies, blob roots, replicas, WAL/archive/log copies and key/config versions during separately authorized implementation/setup, with ownership and deadlines; do not read their contents for today's design.

Recommend native Ubuntu backup sets covering a consistent database snapshot, matching private blobs, deployment/version manifest, privacy register watermark and securely stored recoverable keys/configuration. Backups are encrypted, operator-only and never served by the app. Keys are not included in own-data packages and global key destruction is not an erasure method. Daily policy/RPO ≤24 h and C19 RTO ≤60 min remain targets requiring a complete measured exercise.

Backup capture also participates in privacy concurrency: seal a consistent DB/blob manifest and register watermark under the shared control conventions, with bounded copy leases on owned immutable files. A privacy deadline must abort an incomplete capture rather than silently extend retention; cleanup removes only that capture's owned temporary set. Never publish a backup manifest whose referenced blobs were missed. A set containing pre-redaction bytes remains classified/expiring and cannot be called erased.

The current redaction register/head must survive independently of restoring an older database. Use an append-only authenticated sequence and a durable protected mirror in a separate failure domain approved by the operator; local test directories simulate this, not prove real durability. Persist/reconcile approved intent before destructive steps; fsync durable records and mirror acknowledgment before claiming completion. If no durable mirror/current head is available, deny target access, leave execution/register durability pending and do not claim completed erasure. No external account/service is configured by this design.

Register entries contain namespace/resource/field/action selectors, expected structural generation, monotonic privacy epoch, step/policy version, minimal approval references and a MAC over those non-value descriptors. They contain no erased data or original content/digest samples. Retain selectors only as long as replay is needed. Normal completed erasure and account/session revocation effects are monotonic. An uncommitted/unapproved request cannot create a valid replay instruction; the register receipt must correspond to the committed prepared plan. Distinguish prepared intent from a destructive permit and verified completion. Before the first irreversible primitive, fresh native authorization and a protected target/reference claim must justify a durable permit; lease/source drift blocks further work. A restore executes only a completed descriptor or a latest still-authorized permit, not an arbitrary pending request. Pending/ambiguous intent keeps the target denied and quarantine pending reconciliation. A withdrawal/revocation can cancel only provably unexecuted steps, with its cancellation durably mirrored before acknowledgment; it cannot cancel completed erasure. Interrupted work whose outcome is unknown stays denied until reconciled. Crash between durable intent and DB acknowledgment is reconciled by step identity, not ignored or replayed as a fresh user command.

Restore sequence:

1. Restore into an isolated dedicated testing/restore namespace with outbound mail/tiles, scheduler/workers and ordinary web/download access disabled. Never overwrite development/production as a test. Validate ownership, code/schema/key versions, backup completeness and namespace expiry before reading restored records.
2. Obtain the latest independently authenticated register head. Verify sequence/MACs, backup watermark, monotonic epochs and no gaps; reject an expired/retired namespace. Missing current register/key or unknown target adapter keeps quarantine, not best-effort release.
3. Replay all applicable entries, including intents whose request row is absent in an older backup. A registered approved selector is authoritative for maintenance replay; do not fabricate missing application actors or operational events. Unknown approval provenance stops reconciliation. Known older schema/record generations use versioned replay adapters covering all targeted earlier copies without comparing erased private values; an unknown generation remains quarantined. An absent target is recorded already_absent; later restored files must still be checked.
4. Cover rows, private files, encrypted snapshots/contexts/digests, old exports/packages, mail/job/temp copies and account capabilities together. Do not serve restored CSVs, leases, sessions, reset tokens or old delivery contexts. Rebuild safe caches only from the redacted current source; do not replay historical notification/domain commands.
5. Recompute shared-reference closure on the restored graph. An unexpected older reference is denied/quarantined for reconciliation, not blindly unlinked or made accessible. Treat required missing proof as a current exception, not silently repaired evidence.
6. Verify all due live/backup actions and namespace permissions; resolve any current-role revocation uncertainty before enabling staff access using existing reviewed scope controls. Restoring a backup is not authority restoration. Require fresh authentication against a new restore-generation/session barrier, so prior sessions/package links cannot revive. No blanket user-row rewrite is needed for this barrier.
7. Verify the register head again under the release barrier; replay any newer entries and get an independent release approval. Persist non-sensitive restore outcomes. Enable normal access/workers only when the entire release check is satisfied; incomplete redaction keeps quarantine. Backups awaiting physical expiry are stated as retained, not erased.

A local deletion can finish while a retained backup still contains the data: display live redacted; backup expiry pending until the actual verified expiry. The overall request must not say all copies erased meanwhile. Provider/client copies outside project control are separately disclosed. After the register selectors are retired, old namespace backups must be expired/unusable and rejected outright by the retained namespace marker; never reopen one without a current register.
